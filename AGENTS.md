# AGENTS.md

Руководство для разработчиков и ИИ-агентов по работе с проектом **workflow-engine**.

Распределённый движок выполнения workflow с поддержкой долгих транзакций (long-running transactions) и компенсаций (Saga).

Стек: Python 3.13 (FastAPI, SQLAlchemy 2.0 async, Alembic, Pydantic v2), PostgreSQL 16, React 19 + TypeScript + Vite + Tailwind, Docker Compose, pytest, ruff, mypy.

## 2. Что это за проект

Движок исполняет **дефинишены workflow** — произвольные бизнес-процессы, описанные в JSON: шаги, ветвления, параллельные ветки, ожидания, компенсации.

Ключевая проблема, которую решает проект: **бизнес-транзакция живёт минуты и часы, а транзакция БД — миллисекунды**. Классический ACID не годится. Решение — **durable execution**: транзакция выражается не блокировкой строк, а последовательностью коротких коммитов, записанных в append-only журнал событий.

Демонстрационная предметная область: **заказ → резерв товара → оплата → отправление → подтверждение получения**, с компенсациями на каждом шаге.

## 3. Инварианты движка

Это жёсткие правила. Нарушение ломает корректность восстановления.

### 3.1. Журнал событий — единственный источник истины
- Таблица `workflow_events` — **append-only**. Никаких `UPDATE` и `DELETE` на ней.
  Исключение одно, ADR-0019: уборка архивных процессов старше месяца удаляет их
  журналы, и триггер пропускает удаление только когда сессия объявила уборку и
  база сама убедилась, что процесс терминален и архивен. `UPDATE` запрещён
  всегда. Убранный журнал объявляется пометкой `journal_pruned_at`: процесс с
  пустой лентой без пометки читался бы как «событий не было».
- `seq` внутри инстанса строго монотонен, присваивается под блокировкой строки инстанса.
- Текущее состояние инстанса **выводится replay'ом журнала**. Произвольные `UPDATE workflow_instances SET status=...` запрещены — статус меняется только через запись события.
- Любая бизнес-операция, меняющая состояние инстанса, обязана в одной транзакции БД: (1) записать событие, (2) применить изменение. Если события нет — изменения не было.

### 3.2. Никаких долгих транзакций БД
- Транзакция SQLAlchemy `async with session.begin()` держится **только** на время одного короткого шага: запись события + изменение состояния.
- Запрещено держать транзакцию открытой во время `await` на внешний сервис, `asyncio.sleep`, ожидания таймера или между шагами workflow.
- Если кажется, что нужен «длинный транзакционный блок», — это сигнал, что нужен чекпоинт в журнале, а не блокировка.

### 3.3. Lease вместо распределённых блокировок
- Инстанс обрабатывается **ровно одним воркером** в любой момент, но воркер может умереть в любой момент.
- Координация: колонки `lease_owner`, `lease_expires_at`, `heartbeat_at` в `workflow_instances` + advisory-lock-free захват через `UPDATE ... WHERE lease_expires_at < now()`.
- Никогда не используй `pg_advisory_lock` и не держи блокировку дольше одной операции. Удержание блокировки между шагами — это утечка, которая вешает инстанс навсегда.
- Воркер обновляет heartbeat во время долгого шага. Если heartbeat не обновлялся дольше `lease_ttl_seconds` — lease считается протухшим, инстанс может быть перехвачен другим воркером.

### 3.4. Идемпотентность обязательна
- Доставка событий — **at-least-once**. Exactly-once не существует; имитируем его через идемпотентные обработчики.
- Каждый обработчик шага обязан быть безопасен при повторе: уникальный ключ операции + `INSERT ... ON CONFLICT DO NOTHING` в `processed_operations`.
- **Шаг не может быть повторён, если его эффект уже применён.** Проверка `ProcessedOperation` обязательна в начале обработчика, а не в конце.
- Обработчик не должен делать внешних необратимых действий (отправка email, списание реальных денег) без идемпотентного ключа, передаваемого наружу.

### 3.5. Saga и компенсации
- У каждого шага `action` есть компенсация `compensation`, объявленная в дефинишене явно.
- Компенсации выполняются **в обратном порядке** успешно завершённых шагов.
- Компенсация обязана быть **необратимой и идемпотентной**: её нельзя «компенсировать компенсацией» — она либо успешна, либо нет.
- Падение компенсации — не тихий сбой. Инстанс переходит в `COMPENSATION_FAILED`, компенсация ставится в очередь на повтор, в UI видно ручное разбирательство.
- Компенсация не должна падать из-за того, что компенсируемый шаг «кажется, не завершился». Проверяй факт через `step_runs`, а не через предположение.

### 3.6. Восстановление
- Воркер при старте обязан подобрать инстансы с протухшим lease и продолжить их с последнего durable-чекпоинта.
- Повторное выполнение шага после частичного сбоя должно быть безопасно (см. 3.4).
- Таймеры — durable-объекты в БД, а не `asyncio.sleep` в памяти. Переживают рестарт.

### 3.7. Наблюдаемость обязательна
- Каждое изменение состояния сопровождается событием в журнале. Нет события — нет изменения.
- Тайминги шагов пишутся в `step_runs` (`started_at`, `finished_at`) — без этого невозможно предъявить замеры.
- Ошибки логируются структурно, не через `print`. Никогда не логируются секреты и полные тела внешних запросов.

## 7. Стиль кода

### Python
- ruff, `line-length = 100`, target `py313`. Импорты сортируются автоматически.
- mypy: `disallow_untyped_defs = true` — **все** функции аннотированы.
- Асинхронность: `async def` для всего I/O. Блокирующие вызовы — только через `asyncio.to_thread`.
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов, `_`-префикс для приватных.
- Тип: `Decimal` для денег, никогда `float`. UUID для идентификаторов.
- Комментарии объясняют **почему**, а не **что**. Не комментировать очевидное.
- Docstring на русском для модулей и публичных функций ядра.

### React/TypeScript
- Функциональные компоненты, хуки, TypeScript `strict`.
- TanStack Query или собственная обёртка на SSE — выбор зафиксировать ADR'ом.
- Именование файлов компонентов — `PascalCase.tsx`, страниц — `lowercase.tsx` в `pages/`.
- Tailwind-классы, без CSS-in-JS. Тёмная тема — через CSS-переменные.

### Комментарии
- Комментарий отвечает на вопрос **«почему так»** и не отвечает на вопрос
  «что здесь происходит» — на него отвечает сам код.
- Комментарий нужен там, где причина не читается из текста: неочевидное
  ограничение платформы, обязательный порядок вызовов, ссылка на инвариант
  (§3) или на решение (ADR).
- Пересказ кода удаляется. Он устаревает раньше кода и обесценивает оставшиеся
  комментарии: после трёх пересказов «почему» перестают читать.
- Норма — не квота, а проверка: если строка объясняет имя функции или тип, её
  быть не должно.
- Язык комментария — язык проекта, термины реализации в нём допустимы:
  словарь `docs/UI-GLOSSARY.md` относится к надписям для человека, а не к
  комментариям.

## 8. Правила ведения документации

- Вся документация на **русском языке**. README — тоже.
- Любое архитектурное решение с последствиями → ADR в `docs/adr/NNNN-короткое-описание.md`. Формат — Nygard: Context / Decision / Consequences (Positive / Negative / Neutral) / Alternatives considered / References.
- **Negative последствия обязательны и не могут быть пустыми.** Каждая отклонённая альтернатива приводится с её сильным доводом «за».
- Принятый ADR неизменяем. Новый контекст — новый ADR со строкой `Superseded by ADR-XXX` в старом.
- Схемы — Mermaid, исходники в `docs/diagrams/*.mmd`, вставлены в `.md` через ` ```mermaid `.
- Документация обновляется **в том же коммите**, что и код, который она описывает. Расхождение кода и документации — дефект.

## 9. Работа с git

Полное описание модели — `docs/GIT_WORKFLOW.md`. Здесь обязательный минимум.

### Модель веток

| Ветка | Откуда | Куда |
|---|---|---|
| `main` | — | только релизы, теги на каждой фазе |
| `develop` | `main` | интеграция текущей работы |
| `feature/<scope>-<описание>` | `develop` | `develop` через `--no-ff` |
| `fix/<описание>` | `develop` | `develop` через `--no-ff` |
| `release/<версия>` | `develop` | `main` + `develop`, тег |
| `hotfix/<описание>` | `main` | `main` + `develop`, тег |

- `main` и `develop` вечные. `git push --force` запрещён.
- Ветка удаляется после слияния: `git branch -d`.
- Один `feature` = одна фаза роадмапа (§11) или её логически завершённая часть.

### Формат коммита

```text
<type>(<scope>): <subject>

<body — почему, а не что>

Refs: #<задача>
```

- Один коммит — **одна область**. Изменения в нескольких областях дробятся на
  серию коммитов в порядке «снизу вверх»: `db` → `saga` → `api` → `test` → `docs`.
- Subject до 72 символов, строчные буквы, императив, без точки в конце.
- Тело обязательно, если причина не следует из subject.
- Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `revert`.
- Области: `chore`, `docs`, `infra`, `db`, `journal`, `interpreter`, `lease`,
  `recovery`, `scheduler`, `saga`, `idempotency`, `registry`, `handlers`, `api`,
  `demo`, `frontend`, `test`, `chaos`, `perf`, `refactor`, `fix`.
- Файл, относящийся к двум областям, относится к более узкой
  (`app/engine/saga.py` → `saga`, не `engine`).
- Запрещены `wip`, `tmp`, коммиты без scope, смешивание кода и документации.
- Сообщения — на английском.

### Перед коммитом

Обязательно зелёный `make check`; для изменений кода — также `make test`.
Коммит с красными проверками не делается. Ослаблять правила, чтобы проверки
позеленели, запрещено.

### Релизы

Тег ставится на коммит слияния `release/*` в `main`. SemVer: новая
функциональность — минор, несовместимое изменение — мажор, фикс — патч.
Соответствие фаз и версий — `docs/GIT_WORKFLOW.md` §5.

## 10. Тестирование

- **Порог покрытия — 92% branch-покрытия.** Line-only считается обманом: `if`
  без `else` даёт 100% по строкам при непроверенной ветке.
- Порог задан в `engine/pyproject.toml` (`fail_under = 92`) и включается
  через `--cov-branch --cov-fail-under=92`. Обойти его нельзя молча —
  понижение порога или `# pragma: no cover` без объяснения в теле коммита
  означает ревью всего коммита. Число порога проверяется тестом на согласие
  конфигурации, `Makefile` и документации — иначе эти три записи одного факта
  разъезжаются молча.
- Из покрытия исключены `app/main.py` (точка входа), `alembic/` (миграции) и
  `app/models/base.py` (метаданные без логики).
- Маркеры pytest:
  | Маркер | Что покрывает | Нужна БД |
  |---|---|---|
  | без маркера | unit-тесты, чистая логика | нет |
  | `integration` | транзакции, журнал, lease, HTTP-слой на реальном PostgreSQL | да |
  | `chaos` | падение воркера, таймаут шага, недоступность сервиса | да |
- `integration` **входит** в порог: сервисный и HTTP-слой невозможно проверить
  без настоящей БД, и исключение маркера делало бы порог недостижимым.
  `chaos` не входит — эти тесты поднимают дополнительные процессы и медленны.
- Прогон без поднятой БД: `make test-fast` — только unit, без порога.
- Тест на каждый механизм ядра обязателен. Отсутствие теста на восстановление
  после падения воркера означает недоделанную фазу.
- Ошибка ловится тестом, который падает до исправления. Тест, который и так
  проходит, ничего не проверяет.

## 11. Roadmap по фазам

Каждая фаза — серия коммитов Conventional Commits. Ход работы фиксируется здесь.

### Фаза 0 — Техническое задание `[выполнено, релиз 0.1.0]`
- Каркас репозитория: `engine/`, `frontend/`, `docs/`, `docker-compose.yml`, `.env.example`.
- `README.md` с быстрым стартом.
- `AGENTS.md` (этот файл) + `docs/`: ARCHITECTURE, ENGINE, DATA-MODEL, API, DEVELOPMENT, OPERATIONS, GIT_WORKFLOW.
- ADR-0001 (стек) принят; ADR-0002…0006 зафиксированы в статусе `Proposed`.
- Mermaid-схемы: контекст, подсистемы, исполнение шага, восстановление, компенсации, машина состояний, ER.
- Gitflow и Conventional Commits, порог тогда был 90% (факт прогона: 96%).
- **Результат:** окружение поднимается одной командой, документация соответствует коду.
- Коммиты: 15 штук в `main`, теги `0.0.0` (правила) и `0.1.0` (Фаза 0).

### Фаза 1 — Эскизный проект `[выполнено, релиз 0.2.0]`
- Модель данных и миграции: `workflow_definitions`, `workflow_instances`, `workflow_events`, `step_runs`, `timers`, `processed_operations`, `compensation_log`.
- Схема дефинишена (JSON) + валидация структуры и семантики графа (нет циклов без `loop`, все компенсации разрешаются, все `next` существуют).
- ADR-0002…0006 приняты.
- **Результат:** схема БД создаётся миграцией, дефинишен валидируется, решения зафиксированы.
- Найдено при тестировании: члены `join` — входящие связи; их учёт как исходящих превращал fork/join в цикл.

### Фаза 2 — Технический проект: ядро `[выполнено, релиз 0.3.0]`
- `journal.py` — append-only журнал, последовательности, replay.
- `interpreter.py` — переходы состояний, ветвления, fork/join.
- `lease.py` — захват, heartbeat, освобождение.
- `scheduler.py` — durable-таймеры.
- `saga.py` — компенсации в обратном порядке, повторы, `COMPENSATION_FAILED`.
- `idempotency.py` — `ProcessedOperation`.
- `registry.py` — резолв обработчиков по import-path.
- `executor.py` — исполнение шага: транзакция закрывается до внешнего вызова.
- Unit + integration тесты на каждый механизм, chaos-тесты на падение воркера.
- **Результат:** движок исполняет дефинишен целиком и переживает падение воркера.
- Найдено при тестировании: раздельный `SELECT ... FOR UPDATE` и `UPDATE` захвата
  лишал второго воркера доступа к свободным инстансам; захват пачки оставлял
  воркера держать аренду на необработанных инстансах; удержание аренды после
  неудачного шага откладывало откат до истечения TTL.

### Фаза 5 — Рабочий проект: отладка и испытания `[выполнено, релиз 0.6.0]`
- Отладка каждого механизма (автономная → комплексная).
- Контрольный пример: сбой на шаге оплаты → автоматический откат.
- Тесты: unit, integration, chaos (падение воркера, таймаут шага, недоступность сервиса).
- Замеры: throughput, latency по шагам, время компенсации.
- `engine/scripts/`: `seed` (наполнение), `smoke` (сквозная проверка), `load` (замеры).
- Методика замеров зафиксирована в ADR-0007, результаты — в `docs/BENCHMARKS.md`.
- **Результат:** измеримые характеристики, подтверждённая устойчивость. 300 инстансов:
  1 воркер — 2.8 инстанса/с, 2 — 5.4, 4 — 10.3; шаг ~20 мс, компенсация ~41 мс.
  **Перезамер сделан 2026-10-15:** 3.30 / 6.17 / 10.13 инстанса/с по трём
  прогонам, разброс 0–4 %, шаг 15–28 мс, откат ~29 мс. Масштабирование
  перестало быть линейным на четвёртом воркере (×1.87 и ×1.64), и найдена
  причина: **шаг занимает лишь ~30 % времени цикла**, остальное — захват
  аренды, разбор журнала и проверка таймеров вокруг него.
- Найдено при испытаниях:
  - `wait_before_seconds` из дефинишена нигде не применялся — `interpreter.wait_before()`
    не вызывался, и процесс с ожиданием проходил мгновенно;
  - сработавший таймер не будил инстанс: `claim_due()` вызывался, но результат
    выбрасывался, а `notify_fired()` не вызывался нигде в приложении — инстанс
    навсегда зависал в `WAITING`;
  - спящий `WAITING`-инстанс попадал в `claim_next` и, оставаясь самым старым,
    блокировал очередь: воркер брал его снова, пока тот не просыпался;
  - отметка `fired` и событие `TIMER_FIRED` шли разными транзакциями — падение
    воркера между ними оставляло инстанс спящим навсегда.

### Фаза 6 — Внедрение `[выполнено, релиз 1.0.1]`
- Полный комплект `docs/` актуален и соответствует коду.
- `README.md` — быстрый старт с нуля.
- Акт внедрения: `docs/DEPLOYMENT-ACT.md`.
- Замеры пересняты на машине без посторонней нагрузки: разброс между

- Финальный прогон всех проверок: 383 теста, покрытие branch 93.39%,

- **Результат:** проект готов к сдаче.
- Найдено при внедрении:
  - ветка `next.on_failure` не исполнялась: исполнитель записывал решение

    а работающий воркер держит блокировки, и вместе они дают

### Фаза 8 — Настоящая предметная область и наблюдаемость `[выполнено, релизы 1.2.0 и 1.2.1]`
- **Компенсация отменяет данные.** Раньше обработчики возвращали словари и
  ничего не меняли: резерв не существовал, отменять было нечего. Теперь
  резервирование, списание и отправление пишутся в БД, компенсации отменяют эти
  записи, и откат проверяется по данным.
- **Атомарная идемпотентность.** Проверка ключа, эффект и отметка идут одной
  транзакцией. Раньше окно между проверкой в движке и отметкой после эффекта
  давало повторное применение — безобидно, пока обработчик ничего не делал.
- **Контекст компенсации.** Компенсация вызывалась как `handler(None)` и не
  знала, что отменяет.
- **Ограничение остатка.** `reserved <= available` плюс миграция: заказ больше
  остатка падает как шаг.
- **Страж образца в редакторе.** Опечатка в имени обработчика показывалась
  только при попытке сохранить определение.
- **Интерфейс:** экран состояния с тревогами по таблице из OPERATIONS.md,
  граница ошибок, поиск и сортировка инстансов, пресеты шагов в панели инъекций,
  валидация определения до сохранения.
- **Результат:** откат доказывается данными, границы движка остаются
  задокументированными, интерфейс показывает механику.
- Найдено при доработке:
  - компенсация получала `None` вместо контекста;
  - обработчики ничего не писали, а документация утверждала обратное;
  - `IntegrityError` от нарушения внешнего ключа проглатывался как гонка за
    уникальным ограничением: откат тихо отменял бы применённый эффект;
  - в образце определения — опечатка в обработчике, имя, совпадающее с
    seed, и несуществующий артикул;
  - `session.get` искал товар по первичному ключу вместо артикула;
  - тест `test_compensation_handlers_are_idempotent_noops` утверждал, что
    компенсации ничего не делают.
  - план отката строился по колонке инстанса, а по replay'"у: колонка стоит за шага в текущей итерации и ещё не учётна в нёй, и план отката выродался пустым, хотя резерв уже занят;
  - `retryable` терялся надвух этапах: `_invoke` обёртывал ошибку в `StepFailed(retryable=True)`, и недостатка товара не повторялась — отказ по правилу срашал в `max_attempts` раз;
  - отказ без компенсации писал `INSTANCE_COMPENSATED`, а повтор отката менял статус без события — `replay` весгда отдау и не стал бы повторена.

### Фаза 7 — Наблюдаемость и честные границы `[выполнено, релиз 1.1.0]`
- **Циклы исполняются.** Счётчик `max_iterations` требовался валидатором, но не
  читался кодом: определение с циклом проходило проверку и зависало навсегда.
  Счётчик живёт в `InstanceState` и растёт из журнала; по достижении предела
  пишется `LOOP_EXHAUSTED` и процесс уходит в компенсацию.
- **Параллельные ветки отвергаются валидатором.** Раньше определение с `fork`
  сохранялось, а процесс выполнял префикс графа и отчитывался об успехе.
  Решение и его цена — ADR-0008.
- **Граф шагов на странице инстанса:** послойная раскладка, обратные рёбра
  цикла, цвет узла по фактическому состоянию, полоса фактического порядка
  отката.
- **Наблюдаемость:** payload событий раскрывается, ожидание показывает
  отсчёт по дате из `TIMER_SCHEDULED`, панель аренды и heartbeat, время
  последнего события потока.
- **19 тестов фронтенда:** раскладка схемы, раскраска узлов, группировка
  аренд. Vitest настроен — до этого скрипт `test` был без единого теста.
- **Результат:** границы движка перестали быть неожиданностью для
  пользователя; интерфейс показывает механику, а не только статусы.
- Найдено при доработке:
  - `max_iterations` нигде не использовался: счётчик был обязателен в
    валидаторе и отсутствовал в движке;
  - параллельные ветки проходили валидацию и давали молчаливый полууспех;
  - интерфейс получал ссылку на определение без `id`, из-за чего схему шагов
    было не загрузить;
  - в списке инстансов не отдавался `heartbeat_at`, из-за чего простой и
    молчание воркера были неразличимы.

### Фаза 9 — Разбор стенда: дефекты, производительность, наблюдаемость `[в работе, ветка fix/audit-findings]`
Разбор стенда на живых данных, а не по коду. Найдено шесть фаз, каждая с
тестом, падающим до исправления.
- **Дефекты.** `update()` слал весь объект редактора вместо `{definition, is_active}`
  и получал 422; `mark_applied` глотал нарушение внешнего ключа, выдавая его за
  гонку за уникальным индексом; правило инъекции в режиме `once` не отбиралось;
  редьюсер SSE обновлял состояние вне `set`, теряя события при пакетном обновлении;
  метрики страницы не различали ошибку и «метрик нет».
- **Производительность.** Четыре индекса под горячие пути: на 60 000 событий
  разбор журнала перешёл с 3489 буферов на 204, сортировка ушла совсем.
  Пул соединений уменьшен до 5+5 с таймаутом меньше TTL. Поток событий больше
  не прогонывает всю историю на каждом подключении: курсор по времени,
  событие с `id:`, опрос раз в секунду вместо heartbeat'а. Страница инстанса
  не дёргала пять запросов на каждое событие.
- **Наблюдаемость.** Четыре метрики были объявлены, но не писались: теперь
  подключены к точкам, где случается факт. `Content-Type` объявлял OpenMetrics
  при теле в формате Prometheus — строгий скрайпер отверг бы весь ответ.
  `CycleResult.lease_lost` был объявлен, но не читался.
- **Доступность.** Ошибки не объявлялись скринридеру, заголовки таблиц теряли
  связь с колонками, узлы графа шагов были доступны только мышью.
- **Тесты фронтенда.** Разбор ошибок бэкенда, сборка запросов, подписи
  состояний: 35 → 54 теста. Найдено: неразбираная дата попадала в журнал
  как «Invalid Date».
- **Контракт и чистка.** В трёх местах текст был повреждён кодировкой и
  читался как знаки вопроса.

Не сделано сознательно: порог покрытия фронтенда не задан — для этого нужен
`@vitest/coverage-v8`, а новая зависимость в проект не вносилась без решения.

Найдено при разборе:
- SSE начинал соединение с эпохи и слал всю историю журнала: на каждое
  подключение приходились все события работы стенда;
- частота опроса потока была случайно равна интервалу heartbeat;
- `step_run` после коммита протухает, и чтение его атрибутов из асинхронного
  кода кончалось `MissingGreenlet` — длительность пришлось считать по
  границам, сохранённым в локальных переменных;
- `INSTANCE_STARTED` не входит в публикуемые события, и тест на поток
  проверял событие, которое поток никогда не отдаёт.

### Фаза 10 — Аудит стенда: восемь находок `[выполнено]`
Разбор ведёт себя не по коду, а по живому стенду: каждая находка доведена до
теста, который падает до исправления.
- **Откат.** Инстанс в `COMPENSATION_FAILED` считался активным, но воркер
  отправлял в `_compensate` только `COMPENSATING` и `CANCELLING` — процесс
  возвращался к упавшему шагу и доводился до конца под новым ключом
  идемпотентности. На стенде отменённый процесс достигал `COMPLETED`, а резерв
  оставался. К тому же план отката не отсекал уже откатанные шаги: порядок
  берётся из журнала, где они остаются навсегда.
- **Повторы.** Провалившаяся компенсация повторялась каждый цикл, то есть раз
  в секунду на воркер. Добавлена пауза в строке инстанса с ростом по попыткам.
- **Интерфейс.** Страница инстанса опрашивала четыре запроса каждые 1.5 с даже
  для завершённых процессов, список — каждые 2 с при живом потоке. Ответы не
  отменялись: пришедший позже откатывал экран на шаг.
- **Пагинация.** Журнал читался целиком ради первых строк; предел применялся в
  Python.
- **Текст CI.** Тридцать строк файла содержали escape-последовательности
  вместо русского текста, включая имена задач: файл ни разу не выполнялся.
  Добавлен тест, ловящий возврат такой порчи.
- **Границы обработчиков.** Определение из редактора могло указать `os:system`.
  Ограничение корней модулей настройкой, ADR-0013.
- **Расхождения.** Версия в OpenAPI разошлась с пакетами; две ручки не были
  описаны.
- **Найдено попутно:** панель инъекций не умеет ломать компенсацию — правило
  сверяется с именем шага, а не обработчика отката. Не исправлено: вне объёма.

### Фаза 11 — Разбор кода и новая функция `[в работе, ветка fix/audit-findings]`
Ревью всего проекта, а не только стенда: шесть дефектов движка, четыре — интерфейса,
уборка текста и один новый сценарий.
- **Аренда.** Потерянную аренду никто не проверял перед записью результата: шаг
  длиннее TTL давал два `STEP_COMPLETED`. Теперь запись разрешена только владельцу,
  а `LeaseLostError` действительно выбрасывается.
- **Откат.** `_compensate` не продлевал аренду — откат длиннее TTL запускался
  вторым воркером. Ключ компенсации рос с номером попытки, и падение между
  эффектом и отметкой возвращало средства дважды. Ручной повтор отката не снимал
  паузу, и кнопка молча не работала.
- **Кэш определений** проверял только идентификатор: правка в редакторе не
  доходила до работающего воркера до перезапуска.
- **Интерфейс.** Поиск и сортировка в списке считались и выбрасывались. Три
  страницы опрашивали API по-разному, ответы не отменялись, поток не проверял
  порядок: повторный кадр возвращал завершённый процесс в «выполняется».
- **Текст.** Около тридцати пяти комментариев были повреждены правкой через
  консоль, включая две видимые пользователю надписи. Стража теперь ищет конкретные
  случаи порчи, а не escape-последовательности.
- **Мёртвое.** Три типа событий существовали в перечислениях, разборе, потоке и
  типах интерфейса, и не писались никогда. `STEP_RETRY_SCHEDULED` объявлен
  молчащим осознанно, и теперь любое событие обязано быть либо в потоке, либо
  в списке молчащих — это проверяет тест.
- **Новое: пауза по решению человека** (`wait_for: manual`, ADR-0014). Ожидание
  человека и ожидание внешнего сигнала не выражаются выдуманным числом.
- **Разрез метрик терял статусы.** `PENDING` и `CANCELLING` не попадали в
  разрез, и страница показывала по ним ноль — то есть утверждала, что таких
  процессов нет. Сверка списка с перечислением движка теперь проверяется тестом.
- **Тесты компонентов.** Без разметки страницы не исполнялись, а отчёт покрытия
  их не считал: 91 % на половине файлов. Среда появилась, честная цифра
  оказалась 47 %, и подъём до 94 % потребовал отдельной очереди по всем
  страницам и компонентам.
- **Тест-раннер обновлён до Vitest 5.** Четыре уязвимости в дереве, из них
  критическая — выполнение кода через `tinypool`; сборку они не затрагивали,
  но оставались в `package-lock.json`. Все 209 тестов перешли без правок,
  а девять новых добавлены по разрывам, которые вскрылись.
  Числа покрытия упали — и это не потеря тестов: Vitest 4 переписал подсчёт V8
  на анализ AST вместо `v8-to-istanbul`, и прежние 93 % часть строк не считали.
  Порог переставлен на достигнутое, а потом, когда долг закрыт, поднят ещё раз:
  90/80/91/92 → 94/83/96/96.
- **Долг по покрытию закрыт.** Названный после обновления раннера долг — `pages`
  и `store` около 70 % по веткам — разобран: 83.5 % веток, 96.3 % функций.
  Восемнадцать новых тестов, все на настоящие пути.
- **Что нашёл этот разбор.** Загрузка списка инстансов была покрыта **только в
  отменённом виде**: ни успешной загрузки, ни ошибки — а от них зависит каждая
  страница. Нечитаемый JSON в редакторе и в поле входа давал человеку сообщение
  движка JavaScript вместо объяснения. Два поля инстанса на панели инъекций
  назывались одинаково, и тесты обходили это селектором.
- **Моки-обёртки проглатывали аргументы.** Проверки «инъекция адресована тому
  инстансу» физически не могли увидеть адрес — шпион получал пустой вызов. Такая
  проверка проходит, ничего не утверждая, и хуже отсутствующей.
- **Что нашли тесты компонентов.** Два поля адреса инстанса в панели инъекций были
  связаны одним значением, и адрес для инъекции молча применялся к остановке
  аренды. Полоса отката показывала прямой порядок выполнения при правильной
  нумерации — читать приходилось снизу вверх. Подпись шага на графе открывалась
  только по наведению мышью. Застрявший на откате процесс предлагал две кнопки
  в одно состояние, причём более медленную из них.
- **Страж текста.** Он был словарём известных случаев и новую порчу пропускал:
  в дереве оставалось 44 повреждённые строки. Теперь ловится сам класс — три
  вопросительных знака подряд или знак замены.
- **Откат наконец можно уронить** (`POST /api/chaos/fail-compensation`, ADR-0015).
  Раньше ломался только прямой шаг, и главный сюжет Saga — провал компенсации —
  нечем было показать. Правило адресуется обработчиком отката, а не именем шага:
  шаг уже выполнен, и правило по его имени сработало бы на прямом шаге.
- **Необратимое под вопросом.** «Завершить без компенсаций» стояла рядом с
  «Отменить» и отличалась от неё одними словами, хотя стоит несопоставимо
  дороже: выполненные шаги остаются, и отменить это уже нельзя. Видимый фокус
  добавлен: на тёмном фоне штатное кольцо браузера почти не читается.
- **Сквозные проверки через браузер.** Их не было вовсе: CI проверял бэкенд,
  chaos, фронтенд и API-смоук, но ни одна проверка не открывала интерфейс.
  Класс дефектов «экран показывает одно, а система делает другое» ловился
  чтением и ручным обходом. Добавлен Playwright и пять проверок: пауза
  называется на странице одним и тем же, отсчёт показывает свой срок,
  необратимое завершение спрашивает, сломанный шаг приводит к откату,
  сломанная компенсация оставляет только повтор отката. Три первых — регрессии
  на дефекты этого разбора; каждая падает при откате своей правки.
- **Ошибка в консоли, которой не видно.** Браузер просил `/favicon.ico` и получал
  404 на каждой странице. Не видно глазом — единственный признак был в консоли,
  которую во время показа не открывают. Консоль проверяется сквозными, но с
  оговоркой: headless-браузер значок не запрашивает, и именно этот отказ
  проверка не увидит — его нашёл только браузер с окном.
- **Срок ожидания человека закрыт** (`pause_timeout_seconds`, ADR-0016) — долг
  из ADR-0014. Пауза без срока висела навсегда: `PAUSED` не берётся воркером,
  будить было некому. По истечении срока процесс **отменяется** и уходит в
  откат: действие шага необратимо, и «платить без согласования» — не то, что
  означают ворота согласования. Срок пошаговый и по умолчанию отсутствует;
  планируется тем же durable-таймером с видом `pause_deadline`, потому что на
  шаге могут стоять и ожидание, и срок, а различать их больше нечем.
- **Что нашёл разбор при этом.** Отсчёт ожидания брал **первый** таймер в
  журнале: у процесса, который сначала ждал таймер, а потом встал на паузу,
  показывался срок уже отбывшего ожидания. И пауза показывала прочерк вместо
  срока — «ждёт решения» и «ждёт, пока не отменится» выглядели одинаково.
- **Осмотр живого интерфейса нашёл собственную ошибку.** Планирование срока
  пишет `TIMER_SCHEDULED` — тем же событием, что и ожидание шага, — и разбор без
  оглядки на вид переводил паузу в `WAITING`. На экране одно состояние
  называлось двумя словами: шапка «Ждёт решения», карточка «Ожидание» (§3.1).
  Тесты этого не видели: они проверяли колонку, а не разбор.
- **Сырые имена состояний прогона.** У прогона шага был тон, а подписи не было:
  таблица и журнал показывали `COMPLETED` посреди русского текста. Добавлен
  словарь подписей — по образцу подписей состояний процесса.

### Фаза 12 — Стенд, который молчал `[выполнено]`
Разбор стенда начался с того, что человек увидел очередь, которая не разбиралась.
Каждая находка доведена до строки в коде, а не до объяснения.
- **Адрес БД подставлялся в контейнеры.** `${DATABASE_URL}` в compose берётся из
  оболочки, а адрес хостовых скриптов — `localhost:5434`. Заданный в оболочке,
  он уезжал внутрь контейнера, где такого хоста нет: воркер уходил в бесконечные
  попытки соединения, **оставаясь «живым»**, и очередь стояла 42 минуты без
  единого признака на экране. Адрес внутри сети теперь литеральный — как у
  сервиса миграций. Семь проверок стерегут этого, и они доказаны откатом: с
  подстановкой на месте падают все три сервиса.
- **Страж сначала ругался на сам себя.** Проверки читали и комментарии, а
  комментарий, объясняющий запрет подстановки, цитирует её дословно. Теперь
  комментарии отбрасываются: страж смотрит на конфигурацию, а не на текст.
- **Инструменты мерили не то определение.** Замерщик и смоук брали «первое
  активное». Активных определений на стенде оказалось два, и одно ждало
  доставку час — смоук падал с «процесс не дошёл до конца за 30 с», что не
  говорит о движке ничего. Оба теперь выбирают по имени.
- **Проверка ждала невозможного.** «Недоступный товар не оставил резерва»
  требовала нуля, а подтверждение доставки склад не трогает (ADR-0006), поэтому
  резерв накапливается у каждого завершённого заказа. Проверка проходила только
  на пустой базе и объявляла утечкой чужой резерв. Теперь сравнивает снимки
  «до и после».
- **Уборка сквозных ломала их сами.** Проверки выключали созданное ими
  определение, а на следующем прогоне брали его по имени, не включив обратно:
  второй прогон падал с «определение неактивно». Теперь включает при каждом
  обращении.
- **Числа в акте внедрения не сходились с действительностью.** Заявлено 415
  тестов и 93.03 %, на деле 472 и 93.35 %; в одной строке стояло «433 теста
  (444 движка и 29 фронтенда)» — само себе противоречие. Приведено к замеру.
- **Осталось незакрытым (закрыто в Фазе 14).** Перезамер `BENCHMARKS.md`
  сделан 2026-10-15; числа с 1.2.0 заменены. Требовавшее решения подтверждение
  доставки вынесено в ADR-0020, хранение журнала — в ADR-0019; оба в статусе
  `Proposed`, кода по ним нет.

### Фаза 14 — Перезамер и два спорных решения `[выполнено]`
Последние цифры работы и два решения, которые нельзя было принять молча.
- **Замер переделан с нуля, а не дополнен.** Прежние числа относились к
  релизу 1.2.0, то есть к коду до исправлений отката и повторов. Снято три
  прогона на каждую конфигурацию, по методике ADR-0007: прогрев не публикуется,
  очередь перед прогоном пуста, склад обнулён.
- **Первый прогон разошёлся на 20 %, и причина была не в движке.** На машине
  шёл Steam. После его закрытия тот же код дал 3.3, 3.3, 3.3 инстанса/с.
  Прежняя редакция документа обещала единицы процентов на свободной машине —
  обещание подтвердилось, но выяснилось, что оно держится на дисциплине, а не
  на свойстве системы. Это записано оговоркой, а не сглажено.
- **`docker compose up -d --scale worker=N` поднимает весь стенд.** Без
  `--no-deps` и без имени сервиса стартуют ещё и фронтенд, и второй сервис
  воркеров: лишний контейнер тихо отнимает ресурсы, и замер этого не показывает.
  В методику внесена правильная команда и проверка через `/api/workers`.
- **Масштабирование перестало быть линейным, и найдена причина.** 1 → 2 воркера
  дают ×1.87, 2 → 4 — ×1.64. Причина в измерениях шагов: с ростом числа
  воркеров шаг удлиняется с 18 до 24 мс, то есть каждый воркер обрабатывает
  меньше шагов в секунду.
- **Главная находка: шаг занимает лишь ~30 % времени цикла.** Остальное — захват
  аренды, разбор журнала и проверка таймеров, и всё это повторяется на каждом
  шаге. Отсюда вывод, которого раньше не было: уменьшать
  `WORKER_POLL_INTERVAL_SECONDS` бесполезно — при непустой очереди цикл не
  доходит до ожидания. Помогло бы пакетное исполнение и кэш разбора по `seq`;
  ничего из этого не сделано, замер фиксирует состояние кода.
- **Создание инстансов с ростом воркеров замедляется**, а не ускоряется, как
  утверждала прежняя редакция документа: 2.0 → 2.2 → 2.6 с. Утверждение
  исправлено.
- **Остаток прежних чисел в документе заменён полностью**, вместе с оговоркой
  про переносимость и с указанием, какие числа к какому коду относятся.
- **Два решения вынесены в ADR и оставлены `Proposed`.** ADR-0019 (уборка журнала
  по возрасту) и ADR-0020 (когда резерв покидает склад) касаются собственных
  утверждений работы, поэтому код по ним не написан: сначала решение, потом
  реализация. Реестр ADR в `docs/adr/README.md` отстал на 0015…0018 — дополнен.
  Позже оба приняты и реализованы; состояние реестра приведено к факту.
- Найдено при замере:
  - прогон на загруженной машине дал 2.3, 2.4, 2.8 инстанса/с — на 20 %
    больше разброса, чем на той же машине без посторонней нагрузки; вывод
    «шум машины не влияет» был неверен, хотя раньше это же утверждалось в
    документе;
  - стенд стоял на запущенном Docker с остановленными контейнерами, включая
    соседний проект, и об этом узнали только по неотвечающему API.

### Фаза 15 — Язык и мера `[в работе, ветка develop]`
Релиз 1.3.0 закрыл механику; эта фаза приводит в порядок то, как работа выглядит
снаружи и как она измеряется.
- **Язык сообщений движка.** Интерфейс перевели на язык продукта, а движок
  продолжал отвечать своими словами: ошибка API на экране читалась как «инстанс не
  найден», метрика несла подпись «Потерянные аренды», панель неисправностей
  считала «активные инъекции». 34 сообщения и подписи переведены, добавлен страж
  `test_engine_wording.py`: он читает `app` деревом и проверяет строковые
  литералы, исключая docstring'и. Отдельный тест требует, чтобы страж вообще
  что-то читал: пустой набор находок проходит «слов нет» вечно.
- **Комментарии движка.** Фронтенд прошёл этот приём раньше, движок остался со
  своими правилами: шапки пересказывали следующие десять строк, docstring'и
  повторяли инвариант, который сами цитировали, а тесты рассказывали историю
  дефекта, уже записанную в роадмапе. Снято 121 строку. Осталось то, чего не даёт
  код: транзакция закрывается до внешнего вызова, в ключ компенсации не входит
  номер попытки, словарь не отличил порчу от склонения.
- **Порог покрытия 90 → 92.** Выбран по худшему прогону: `make test` без chaos
  даёт 92.37 %, полный — 92.98 %. 93 % прошло бы на полном прогоне и упало бы на
  `make test`, то есть порог зеленел бы и краснел от того, какие тесты запущены.
- **Страж чисел.** Одно число записано в трёх местах — `pyproject.toml`,
  `Makefile` и документация, — и все три разошлись: акт внедрения называл старый
  порог при старом покрытии, `DEVELOPMENT.md` — 83/96 при конфигурации 84/97.
  `test_coverage_thresholds.py` требует согласия всех записей и запрещает
  понижение ниже 90. Доказан откатом: с прежним порогом падают восемь проверок.
- **Что нашлось попутно.** Странгуя комментарии, я правил `test_lease_batch.py`
  по поводу неиспользуемой переменной — она была мёртвой ещё до этой фазы.
- **Репетиция глазами стенда.** Сквозные проверки проходят все двенадцать
  сценариев и тринадцать проверок стенда, но находки репетиции — не те, что они
  ловят:
  - **Проверки оставляли мусор, которого никто не ждал.** Три процесса из
    `stand.spec.ts` уходили в паузу и оставались там навсегда: на защите в списке
    висят три заказа под именем `e2e_manual_gate`, которых никто не заказывал, а
    на складе висит их резерв — панель показывает удержание без объяснения.
    Уборка в `afterAll` отменяет свои паузы и ждёт терминального состояния; страж
    `zz_cleanup.spec.ts` идёт последним и падает, если у схем проверок осталась хоть
    одна пауза. Доказан откатом: с убранной отменой страж падает.
  - **Архив недоступен поимённо** — эндпоинт берёт только возраст, поэтому
    убранное остаётся в списке терминальным, и его снимает кнопка уборки. Это и
    делает человек перед показом.
  - **Шестьдесят примеров в документации набраны на порт по умолчанию.** На стенде
    с занятым портом команда «не сработала бы» и выглядела бы как поломка движка.
    Вместо правки шестидесяти строк в §1 сказано, что адрес берётся из `API_PORT`.
  - **Сценарий быстрее, чем взгляд.** Замер: от 0.4 с (заказ больше остатка) до
    30 с (истёкший срок ожидания), каталог подряд — 1.8 минуты. Полсекундный
    сценарий на защите выглядит как «ничего не произошло», и записано, что с этим
    делать: называть вслух до нажатия и показывать ленту времени с пробелами.
  - **Имена шагов латиницей на экране.** Рядом с подписью «Платёж отклонён»
    зритель читал `charge_payment`: словарь держался на словах вокруг, а само имя
    шага осталось данными. Заголовком шага стало описание из схемы (`description`,
    оно там уже было), имя осталось вторым текстом и подсказкой. Словарь имён во
    фронтенде был бы второй копией данных схемы: правил схему — правь два места.
    Применено в карточке состояния, таблице прогонов, ленте времени, полосе
    компенсации и фразах журнала; в узлах графа, списке инстансов, отчёте и
    редакторе осталось имя — там оно и есть идентификатор. У счётчика проходов
    цикла осталось имя намеренно: «Проверка корзины перед любым побочным
    эффектом: 3» — фраза, из которой не видно счёта.

- **Отмена была видна только в журнале.** Отмена процесса с выполненными шагами
  приходит в `COMPENSATED` — так же, как сбой, — и на вопрос «это отмена или
  ошибка?» надписей на экране не было. Разбор журнала факт помнил
  (`cancel_requested`), но наружу поле не отдавалось: ни `InstanceOut`, ни
  `InstanceStateOut`. Теперь отдаётся, и под бейджем на странице процесса стоит
  «Отменён, изменения возвращены». Новое состояние не заводилось: факт уже лежит в
  журнале, а состояние — его чтение (§3.1); колонка `cancel_requested` была бы
  вторым источником истины. Подпись проверяется и на правдивость: у процесса,
  упавшего самому по себе, её нет. В `OPERATIONS.md` §8 записан готовый ответ на
  вопрос комиссии и граница: в списке отмена не ищется, фильтр идёт по состоянию.
  Доказан откатом: со снятым полем проверка API падает.
- **Словарь оказался виноват в порче текста.** Он запрещает «прогон» в надписях и
  предлагает «выполнение шага», и эта замена прошла по исходникам целиком —
  комментарии и названия проверок тоже. Осталось четырнадцать мест вроде
  «выполнение шагаы по времени начала» и «полного выполнения шага»: слово на
  месте, смысл перепутан, читается как законченный текст. Исправлены по смыслу
  своего контекста — у прогона шага осталось «выполнение шага», у прогона проверок
  вернулось «прогон». Стража на этот класс (`brokenWording.test.ts`) ловит
  грамматикой, а не словарём: «выполнение шага» — родительный падеж, и окончания
  за ним быть не может. Первая версия стража не срабатывала никогда: `\b` в
  JavaScript работает по ASCII, кириллица за кавычкой словом не считается, и
  граница не совпала. Доказан откатом дважды.
- **Порог покрытия фронтенда 94/84/96/97 → 95/85/97/97.** Поднимать рано было не на
  чём: долг лежал в графе шагов (82.5 % строк), то есть не исполнялись пути, по
  которым человек с клавиатуры идёт по схеме. Закрыты поведением, а не числом:
  Enter и пробел открывают шаг, остальные клавиши нет, подпись закрывается уходом
  фокуса или мыши — иначе она висит поверх следующего шага и читается как его
  свойства. Запас по веткам и функциям около сотой доли процента, и это сделано
  намеренно: код без проверки должен падать сразу.
- **Метрики продолжали считать то, чего нет.** Gauge, которому не выставили
  значение, показывает прежнее: `collect_from_db` публиковал только те ряды, что
  нашлись в базе, а пустая таблица не вызывала ни одного `set`. На стенде страница
  состояния показывала «14 успешных списаний» при таблице без единой строки — это
  хуже нулей, потому что выглядит как работающая система. Счётчик состояний такого
  не делал: он публикует все состояния перечисления с явными нулями. Ряды шагов и
  компенсаций теперь обновляются всегда, а имена берутся ещё и из схем: шаг,
  объявленный, но не выполненный, системе известен.
- **Границу молчания приходилось угадывать, и она врала.** Реестр зовёт исполнителя
  не отвечающим, если сердце старше трёх интервалов опроса, а сердце писалось раз
  за цикл, и цикл умеет выполнить сто шагов. Замер под нагрузкой (120 процессов,
  два исполнителя, 40 опросов): 14 миганий «не отвечает» на двух занятых. То есть
  система называла мёртвым того, кто работает, — ровно то, что реестр отменил своим
  появлением (ADR-0018). Теперь сердце подтверждается и внутри цикла, и из цикла
  продления закрепления во время долгого шага; тот же замер даёт ноль.
- **Что осталось за границей правки.** Ряд метрики, чьего имени нет ни в базе, ни
  в схемах, живёт в общем файле процессов (ADR-0012), и движку уже неоткуда его
  обнулить. Записано правилом: после прогона `pytest` по базе стенда стенд
  пересоздают. Сегодня это и случилось — тесты обнулили стенд, и показывать было
  нечего.
- **Цикл откатывал только последний проход.** Репетиция на стенде прошла весь
  каталог, и склад после неё держал три единицы, которых никто не заказывал.
  Сверка по журналам показала: резерв брался дважды, а возврат случился один раз.
  Причина в трёх слоях, и каждый по отдельности выглядел исправным: план брал
  «последнее выполнение шага», ключ компенсации строился по имени шага, а контекст
  обработчика содержал **тот же** ключ, собранный в другом месте. Вторая и третья
  компенсации приходили под занятым ключом и объявляли успех, не отменив ничего, —
  то есть компенсация, которая не отменяет. Теперь план берёт все неоткатанные
  прогоны шага, ключ включает прогон, а формат ключа пишется один раз и приходит в
  контекст снаружи. Порядок отката при этом группирован по шагу: разбор журнала
  хранит выполненные шаги без повторов, и обратный порядок по проходам недоступен —
  это записано в `ENGINE.md` как граница, а не подано как строгий обратный порядок.
- **Тот же класс порчи текста, что и «выполнение шагаы», нашёлся ещё дважды**, и
  оба раза в `ENGINE.md`: «падение между ним и эффектом и отметкой не быть вовсе» и
  «внешний вызов к недоступен на последствии внешней отметки ушёл бы видел снова
  повторный». Страж ловит форму «выполнение шага» с окончанием, а не произвольные
  переставленные слова, и это записано как известное ограничение: словарь языка в
  проекте заводить не будут.

Не сделано сознательно: порог не поднят выше 92 — долга для 93 нет, а обещать
число, которое не выдержит ни один прогон, здесь уже пробовали.

### Фаза 13 — Наглядность и сценарии `[выполнено]`
Интерфейс отвечал на вопрос «какой статус», но не на вопрос «что произошло».
Каждый пункт сначала доводится до работающего состояния, потом до теста, и
только потом коммитится.
- **Журнал читался кодами.** Подпись «Шаг выполнен» не говорила, какой шаг и
  куда перешёл процесс: payload рядом показывал ключи на английском, и
  разбираться приходилось глазами по каждому событию. Теперь то же самое
  собирается в фразу с шагом, попыткой, причиной и следующим переходом.
  Тонкость: без имени шага в payload собирать фразу не из чего, и тогда
  показывается подпись события — «Шаг ?» на экране читается как поломка.
- **Два вида таймера говорили одним предложением.** Срок ожидания человека
  планируется тем же событием, что и ожидание шага, и разбор фразы обязан
  смотреть на вид таймера, иначе страница снова назовёт одно состояние двумя
  словами. Это закреплено тестом.
- **Состояние можно проверить, а не поверить.** Утверждение «источник истины —
  журнал» было только в документации: страница показывала и разбор, и колонку
  рядом, но сравнить их было нечем. Добавлена кнопка — перечитывает состояние
  из журнала и сравнивает с колонкой. Расхождение объявляется дефектом, а не
  прячется: на экране разбора инцидента зелёное «совпадает» там, где значения
  разные, было бы враньём. Расхождение по шагу отдельно: колонка на текущей
  итерации цикла стоит на шаг впереди разбора, и это не нарушение.
- **Дев-сервер в контейнере не видит правок.** Bind-mount на Windows не доставляет
  события файловой системе: страница открывается, консоль чистая, а нового
  элемента нет. Проверка правки в браузере даёт ложный вывод «не работает».
  Лечение — `docker compose restart frontend`, и записано в документацию.
- **Лента времени показала главное.** Одно уточнение стоило пересборки
  замысла: внутри одного инстанса шаги не накладываются — его держит один
  воркер, — поэтому лента показывает не перекрытия, а **пробелы**. Именно они
  несут утверждение проекта: процесс живёт секунды, из них в шагах единицы
  процентов, остальное — ожидание, повтор или решение человека. Таблица
  длительностей это скрывала: в ней все шаги одинаково быстрые и процесс
  кажется мгновенным. На живой проверке с тремя попытками оплаты лента показала
  паузы `+1.2 с` и `+2.2 с` между попытками — то есть политику повторов, которую
  раньше приходилось вычислять в уме.
- **Неразбираемая дата читалась как 1970 год.** Разбор времени молча подставлял
  ноль вместо мусора, прогон попадал в раздачу и тянул за собой весь отрезок.
  Теперь такое значение отбрасывается, а не подменяется.
- **Аренда была именем, а имя ничего не говорит.** Строка «Аренда:
  worker-1» не говорила о главном — что срок истечёт и инстанс освободится сам,
  и именно поэтому падение воркера ничего не оставляет висеть. Теперь владелец,
  живой отсчёт до истечения, возраст heartbeat'а и прямая фраза о том, что
  будет после срока. Истёкший срок показывается как «свободен для захвата», а
  не отрицательным временем: минус в подписи читался бы как ошибка.
- **Истории аренды нет и взять её неоткуда.** В журнале нет событий аренды, есть
  только текущий владелец, поэтому перехват виден вживую, но не сохраняется
  для разбора. События аренды в журнал — это изменение контракта событий, и
  здесь не делается.
- **Исполняемый шаг назван словами.** Полоса на ленте растёт на глазах, но
  движущаяся полоса говорит «что-то происходит», а не «что».
- **Сравнить два процесса оказалось нельзя без общей шкалы.** Две таблицы
  длительностей сравнимы только на глаз: у каждой своя шкала, и процесс,
  прошедший за двадцать миллисекунд, занимал всю полосу так же, как
  провисевший в повторах тридцать секунд.
- **Общий контроллер отменял первую сторону.** Вторая начинала грузиться и
  гасила запрос первой — та оставалась пустой навсегда. Комментарий в коде
  описывал правильное решение, а код делал противоположное.
- **Зависание, которое поймал только внешний предел времени.** Страница грузила
  данные по кругу: объект, возвращаемый хуком, попал в зависимости
  `useCallback`, был новым на каждом рендере, и цепочка «новый колбэк →
  повторный эффект → рендер» замыкалась. `testTimeout` не сработал: цикл идёт
  по микрозадачам и перебивает очередь таймеров.
- **Уборка списка — это архивирование, а не удаление.** Кнопка «очистить
  завершённые» соблазняет удалить строки, и база запрещает: журнал ссылается на
  инстанс с `ondelete="RESTRICT"`, а §3.1 требует, чтобы состояние выводилось
  из журнала. Введена колонка `archived_at` (ADR-0017); убираются только
  терминальные процессы, потому что `PAUSED` и `COMPENSATION_FAILED` ждут
  человека, и спрятать их — значит спрятать незакрытый инцидент. На живом
  стенде уборка убрала 329 процессов и оставила 19 `PAUSED` видимыми.
- **Тесты падали из-за работающих воркеров, а не из-за кода.** Два контейнера
  воркеров поднялись на той же базе, забирали аренду инстансов, которые создают
  тесты, и восемь тестов исполнения падали с «процесс остался в RUNNING».
  Стоп воркеров перед `pytest` — не предупреждение, а условие прогона
  (§10).
- **Воркер был виден только пока работал.** Панель аренды показывала держателей
  инстансов, а простаивающий воркер не оставлял следов: аренды у него нет, и
  число воркеров приходилось смотреть в `docker compose ps`. Введён реестр
  `workers` (ADR-0018): воркер вписывается сам при подъёме и продлевает сердце
  раз за цикл опроса. Упавший **не удаляется** — иначе «воркер молчит» и
  «воркера нет» стали бы одним и тем же. Граница молчания — тройной интервал
  опроса, и она отдаётся вместе со списком: подпись «не отвечает» без цифры
  была бы загадкой. На стенде видно и живых, и штатно остановленных.
- **Падение теста было не про аренду, а про порядок прогона.** Восемь тестов исполнения проходили
  только в полном прогоне: `test_worker_disposes_engine_on_stop` проверял, что
  запись `worker.stopped` дошла до обработчика, а запись INFO не создавалась,
  если кто-то раньше не вызвал `configure_logging` и не понизил уровень корня.
  Тест проходил «по счастливой последовательности», а в одиночном запуске падал.
  Уровень в нём теперь задан явно.
- **Таблица без `TRUNCATE` в фикстуре тихо ломает тесты.** `workers` не попала в
  список очистки, и тесты реестра видели 23 строки от стенда. Обнаружилось это
  падением, а не рассуждением — но упасть могло иначе, и тогда список строк в
  тесте просто оказался бы длиннее ожидаемого.
- **Кириллица через PowerShell-heredoc портится — это уже третий раз.** Правка,
  переданная через консоль, молча вставила иероглифы в ADR, и это поймала
  проверка текста. Все правки с русским текстом идут через `write` или
  патч-файл.
- **Порт настраивался двумя переменными, и это выглядело как настройка.**
  `API_PORT` публиковал порт на машине, а `VITE_API_URL` зашивался в браузер при
  сборке. Смена одной тянула за собой вторую, а признак был один — пустые данные
  на странице без единой ошибки в консоли. Теперь переменная одна: браузер ходит
  в свой origin, а прокси Vite внутри сети знает бэкенда по имени `api`.
  Защищено тремя проверками в `test_compose_addresses.py`, все три доказаны
  откатом: с возвращённым `VITE_API_URL` падают две из них.
- **Сценарий — это не кнопка «запустить».** Пока страница не говорила, что
  процесс пришёл в ожидаемое состояние, она ничего не доказывала: «запустилось» —
  факт о кнопке. Теперь сценарий называет ожидаемое состояние, ждёт конца и прямо
  говорит, если пришёл не туда. Порядок вызовов вынесен в `lib/scenarios.ts` и
  проверяется без разметки: правило ставится **до** запуска и снимается **после**,
  а чужое правило снимается ещё до — иначе сценарий, упавший на середине,
  сломал бы следующий, и виноват оказался бы он.
- **Заголовок карточки был не заголовком.** `Card` клал название в `<header>`,
  то есть в текст без роли: страница с полдюжиной карточек состояла для
  скринридера из безымянных секций. Нашлось это не чтением, а сквозной
  проверкой — она искала карточку по роли заголовка и не нашла. Теперь название
  карточки — `h2`.
- **Строгий режим Playwright ловит то, что не видно глазом.** Поиск карточки по
  тексту секции находит и внешние обёртки, потому что они тоже содержат этот
  текст: три кнопки вместо одной. Искать надо от заголовка вверх до ближайшей
  секции.
- **Темп отвечает на вопрос, которого не отвечают счётчики.** Метрики копятся
  с начала работы, и по ним не отличить «десять процессов за час» от «десять за
  десять секунд». График раскладывает процессы по минутам за полчаса и называет
  пик числом. Текущая минута в окно не входит: она не истекла, и полоса за неё
  всегда была бы ниже соседних — график показывал бы момент просмотра, а не
  темп. Архивные процессы в подсчёте участвуют: иначе нажатие кнопки уборки
  стирало бы график, и это выглядело бы как остановка работы.
- **Отчёт должен пережить стенд.** Экран закроется, контейнер останется, а
  разбор инцидента — нет. Отчёт собирается из уже загруженного, без второго
  запроса, и отдаётся файлом прямо в браузере. В нём есть и доля времени в
  шагах, и состояние из разбора журнала рядом с колонкой, и пометка о расхождении
  между ними.
- **Тест отчёта нашёл враньё в самом отчёте.** Длительность шага прыгала, сумма
  делилась на полное время, и на выходе печаталось «−51500 % времени».
  Отрицательный процент в документе для разбора — не опечатка, а ложь; доля
  теперь печатается только когда обе величины осмысленны.
- **Метрики молчали из-за моей же починки портов.** Браузер переведён на
  свой origin, а прокси знал только `/api`; метрики лежат по `/metrics`, запрос
  уходил в дев-сервер, 404 разбирался как «метрик нет», и страница состояния
  показывала нули при живой системе. Ирония в том, что починка убрала одну
  тихую поломку («сменил порт — страница молчит») и создала другую.
- **Адрес метрик совпадает с маршрутом страницы.** Как только `/metrics` попал в
  прокси, страницу «Состояние» стало нельзя открыть: вместо неё приходил сырой
  текст экспозиции. Разведено по заголовку `Accept`: навигация просит HTML,
  запрос данных — метрики. Нашлось это не чтением, а сквозной проверкой,
  которая пришла на страницу состояния и увидела чужой ответ.
- **Ни один тест не ловит «путь вне прокси».** Юнит-тесты мокают клиент, сквозных
  на страницу состояния не было. Добавлен страж `test_api_paths.py`: он читает
  `client.ts` и требует, чтобы каждый запрашиваемый путь был покрыт прокси.
  Первая его версия смотрела только на `api('/…')` и видела один вызов из
  полутора десятка — то есть проверяла почти ничего и выглядела работающей.
- **Комментарий закрыл сам себя.** В тексте про заголовок `Accept` оказалась
  последовательность «звёздочка, косая черта», которая закрыла блочный комментарий;
  дальше файл читался как код. `tsc` файл принимает, esbuild — нет: проверка
  типов зелёная, сборка и дев-сервер падают. Записано в `DEVELOPMENT.md`.
- **Вкладки фильтра называли состояние, а фильтровали по нему же.** Под
  «Завершённые» попадал ровно один `COMPLETED`, поэтому откатанные,
  отменённые и упавшие не были видны нигде, кроме «Все» — а на стенде их
  большинство, и вкладка выглядела пустой при полном списке. Под
  «Выполняются» не попадали ни ожидающие, ни висящие паузы, а у `PENDING` и
  `WAITING` кнопки не было вовсе. Теперь вкладка — это группа, на ней стоит
  число, и в адресе имя группы, а не одно состояние.
- **Сверка вскрыла пустую проверку в самой себе.** Первая версия стража резала
  тело класса по первой пустой строке, то есть на строке документации, и
  возвращала пустое множество — а «каждое состояние покрыто вкладкой» для
  пустого множества истинно. Теперь есть отдельная проверка, что состояния
  разобраны непусто: ровно так же выглядит проверка, которая ничего не видит
  и потому зелена.
- **Реестр воркеров копился, а заголовок считал не то.** Идентификатор включает
  случайную часть, и имя узла меняется при каждом пересоздании, поэтому каждое
  переподключение добавляло строку: на стенде «12 в системе» означало троих
  работающих, а открывавший панель, чтобы понять, почему процессы стоят,
  находил по списку одних давно ушедших. Теперь заголовок пишет «N отвечают ·
  M молчат · K остановлены», записи старше суток скрыты за переключателем вместе
  со своим числом, а в базе лежат на месте — ADR-0021. Только что остановленный
  виден всегда: он объясняет, почему процессы встали.
- **Сценарий проверял только статус.** `COMPENSATED` бывает и у процесса, у
  которого резерв остался на складе, поэтому «пришёл в ожидаемое состояние» —
  это утверждение о кнопке, а не о свойстве. Теперь у каждого сценария есть
  свидетельства из журнала: компенсация реально завершилась, шаг выполнялся
  дважды и завершился один раз, цикл исчерпан.
- **Каталог сценариев вырос с трёх до двенадцати** — по одному на каждое
  свойство: повтор шага, повтор отката, нехватка товара, отмена, долгое
  ожидание, пауза человека, срок ожидания, исчерпание цикла, истечение аренды.
  Заработало это после того, как у сценариев появились определения с
  ожиданием, паузой и циклом: раньше запускать было нечего.
- **Свидетельство ссылалось на данные, которых нет.** Компенсации в
  `step_runs` нет — она живёт в журнале событием `COMPENSATION_COMPLETED` с
  полем `for_step`, а прогоны шагов называются именами шагов графа, а не
  обработчиков. Найдено живым прогоном: в моках всё было зелёным.
- **Падение компенсации терминально для движка, но не для сценария.** Воркер
  берёт откат снова после паузы, а страница объявляла неудачей работу
  повторов. У сценария появились состояния по дороге и предельный срок: без
  часов ожидание превращается в «идёт» независимо от того, что происходит.
- **Глобальное правило съедал чужой процесс.** Правило инъекции без инстанса
  подходит любому, и оставшийся от прошлого сценария процесс в
  `COMPENSATION_FAILED` забрал правило «сломать один раз»: сценарий показал
  успех, не показав ничего. Повтор отката переписан на честный: снять
  причину и повторить вручную — так видно и кнопку разбора, и идемпотентность.
- **Резерв никогда не покидал склад.** Снимался он только откатом, поэтому
  каждый успешный заказ уменьшал остаток навсегда: за месяц показа склад
  пустел, и сценарий «товара не хватает» начинал срабатывать не из-за ошибки,
  а из-за истории стенда. Теперь резерв снимается при подтверждении доставки —
  ADR-0020, уточняющий ADR-0006, где доставка считалась обратимой.
- **Компенсация доставки была недостижимой.** Откат строится по успешно
  завершённым шагам, а шаг последний ничем не сорвать: компенсация жила в
  схеме и не выполнялась бы никогда. В определения добавлен шаг после
  доставки — он и нужен, чтобы возврат резерва кто-нибудь проверял.
- **Возврат резерва может не пройти, и это видно.** Товар забрал другой заказ —
  обработчик поднимает постоянную ошибку, процесс уходит в
  `COMPENSATION_FAILED`. Записано в ADR как отрицательное следствие: на
  защите об этом лучше сказать заранее.
- **Уборка журнала упёрлась в защиту, и это оказалось содержанием решения.**
  Триггер «append-only» запрещает `DELETE` на уровне базы — следовательно,
  «убирать по возрасту» нельзя было ни тихо, ни красиво: можно было либо
  отменить уборку, либо сознательно добавить служебный путь. Выбран путь, где
  проверку состояния процесса делает сама база, а не скрипт: ошибка в отборе
  уборки не может удалить журнал живого процесса — ADR-0019.
- **Пустой журнал без пометки — ложь на экране.** Кнопка сверки сравнивает
  разбор с колонкой и называет разницу дефектом; для убранного журнала разница
  выдуманная. Теперь у процесса с убранным журналом страница объявляет уборку
  и не предлагает сверку.
- **Граница глобальной инъекции объявлена, а не убрана.** Правило без инстанса
  подходит любому процессу, и одноразовое достаётся тому, кто спросил первым.
  На стенде это съел процесс от прошлого показа, а сценарий честно отработал и
  доказал не то — хуже всего, что выглядело успехом. Теперь каталог не зависит
  от одноразовых правил, а страница предупреждает о незакрытых откатах — ADR-0022.
- **Сценарий обещал перехват другим воркером, а на стенде был один.**
  Инстанс поднимал тот же воркер, статус доходил до конца, и недоказанное
  выглядело доказанным. Формулировка теперь называет, что сценарий доказывает на
  одном воркере, и условие для второго — с командой и сверкой через реестр.
- **Пакетный захват измерен, и выигрыша нет.** Гипотеза была внятной: шаг
  занимает ~30 % времени цикла, сократи число захватов — выиграешь. Реализовано
  (ADR-0023), замерено на четырёх конфигурациях: на одном воркере хуже на 7 %,
  на четырёх лучше на 5 % при разбросе 8–12 %. Разница внутри шума. Поэтому
  `WORKER_CLAIM_BATCH` по умолчанию равен 1: механизм написан и покрыт тестами,
  но обещать выигрыш, которого нет, нельзя. Числа и метод — в BENCHMARKS §4.1.
- **Тесты падали из-за работающих воркеров, а не из-за кода.** После замера
  контейнеры остались подняты, и тестовые инстансы забирал живой воркер: три
  теста падали, один — висящей блокировкой. Это ровно правило §10, нарушенное
  мной же в том же прогоне; в BENCHMARKS ничего не попало.
- **Реестр ADR никто не сверял.** ADR-0021 и ADR-0023 появились на диске, а в
  `docs/adr/README.md` их не было, и у 0019/0020 остался `Proposed` при написанном
  коде. Записи писались в трёх форматах шапки, так что и сам парсер различал их
  не сразу. Добавлен страж: каждая запись в реестре, каждая ссылка открывается,
  статус совпадает. Доказан откатом — с убранной строкой 0023 тест падает.
- **Репетиция записана как чек-лист.** Показ отличается от «должно работать»:
  за десять минут до него выясняется, что правило инъекции осталось с прошлого
  сценария и ломает первый же. Раздел 8 `OPERATIONS.md` проходит путь целиком и
  говорит прямо, что показывать нельзя: перехват другим воркером на одном
  воркере не происходит.
- **Сценарии зависели друг от друга, и это было видно как «работа движка».**
  Человек начал сценарий, не дождавшись итога предыдущего. Правило инъекции на
  стенде одно, а снятие у нового сценария общее: второй снял поломку первого, и
  «Откат не проходит» показал заказ, прошедший корректно. Кнопка блокировалась
  только на время запуска, а не на время показа. Страница теперь держит один
  сценарий за раз и говорит почему; два теста на страницу и один сквозной.
- **Двенадцать сценариев подряд, в одной вкладке.** Раньше каждую проверку каталога
  начинали с чистого правила, и такая уборка не проверяла ничего: она скрывала
  именно ту зависимость, ради которой всё и затевалось. Сквозная проверка гонит
  каталог целиком в порядке объявления.
- **Двенадцатый сценарий не доказывал ничего, и это было видно только на стенде.**
  «Срок ожидания истёк» объявлял паузу наблюдаемым состоянием, то есть заканчивал
  показ на паузе: ни срок, ни отказ по нему не проверялись, хотя сценарий говорил
  ровно об этом. Наблюдение оставлено только тем состояниям, на которых
  срабатывает действие, — и это закреплено стражем на весь каталог.
- **Проверка склада требовала несуществующего.** Она требовала нулевого резерва по
  всем артикулам и проходила только на пустом стенде: сценарий «откат не проходит»
  оставляет резерв в силе по замыслу. Снимок «до и после» тоже не годился — резерв
  двигают повторы чужих откатов между двумя чтениями. Свидетельство теперь из
  журнала самого процесса: доставка вернула ровно заказанное.
- **Фронтовые тесты падали не из-за нагрузки, а из-за гонки в самой странице.**
  Два полных прогона подряд упали на разных файлах, и падение «собирает отчёт
  без второго запроса» показало причину: страница процесса грузила данные дважды.
  Она начинает с двухсекундного интервала — статус ещё не прочитан — и переходит
  на «не опрашивать», как только статус известен, а хук на смену интервала
  отвечал немедленной перезагрузкой. Первое открытие страницы стоило четырёх
  лишних запросов, и падал не тест, а код. Смена частоты теперь только
  переносит следующий запуск, а немедленный остаётся один — при появлении хука.
- **«Заморозка» таймеров, которая двигает время, не замораживает ничего.** Тест
  отчёта брал `useFakeTimers({ shouldAdvanceTime: true })` и называл это замиранием:
  время шло, опрос срабатывал между снятием счётчика и проверкой, и утверждение
  «второго запроса не было» падало само по себе. Сдвигать время нельзя — сдвиг и
  есть тот запрос, которого быть не должно.
- **Сон вместо ожидания — это проверка на удачу.** Два теста ждали «600 мс» и
  «2100 мс», а опрос идёт раз в две секунды: окно ожидания совпадало с опросом
  и падало при задержке машины. Теперь эти проверки идут на завершённом процессе,
  где опроса нет вовсе, а проверка цикла ждёт сам цикл с потолком.
- **Прогон, пропустивший половину файлов, выглядел успешным.** Пул проверок
  поднимал по процессу на файл, и под нагрузкой часть воркеров не отвечала на
  старте: ошибка приходила «необработанной», а итоговая строка писала «213 тестов
  прошли» вместо 434. То есть сбой инфраструктуры выдавался за зелёный прогон.
  Число процессов ограничено четырьмя, под той же нагрузкой три параллельных
  прогона дали по 434 теста. Потоки вместо процессов пробовались — старт быстрее,
  но тот же набор идёт вчетверо дольше, 83 секунды против 20. Настройку стережёт
  тест: вернувшийся лимит заметен только по нему.
- **Упавшее соединение роняло проверку, а не движок.** Обращение к API из
  подготовки состояния падало с `socket hang up`: браузерная проверка
  переиспользует соединение, а сервер закрывает его по таймауту. Движок был
  здоров. Идемпотентные обращения теперь повторяются один раз, а создающие
  процесс — нет: повтор создал бы два процесса и проверяла бы не тот.
- **Язык интерфейса переведён на язык продукта.** «Инстанс», «откат»,
  «воркер», «аренда», «дефинишен», «инъекция», «прогон шага» — слова
  внутреннего устройства; на экране их быть не должно. Словарь и обоснование —
  в `docs/UI-GLOSSARY.md`, страж `frontend/src/lib/uiLanguage.test.ts` читает
  исходники без комментариев и падает на этих словах. Первая версия стража
  пропускала всё: `\b` в JavaScript работает по ASCII, и кириллица рядом с
  кавычкой словом не считается — проверка молча показывала «три находки»
  вместо ста тридцати двух.
- **Комментарии укорочены до «почему».** Модульные шапки переписаны: было 579
  строк комментариев в `src`, стало 422, а правило §7 теперь прямо запрещает
  пересказ. Что было сказано только в комментарии и объясняло границу
  системы, перенесено в документацию.
- Все девять пунктов наглядности закрыты.

## 12. Частые ошибки

| Ошибка | Почему это неверно |
|---|---|
| `UPDATE workflow_instances SET status` напрямую | Нарушает §3.1 — состояние только через журнал |
| `DELETE` по журналу «просто для уборки» | Нарушает §3.1: удалять события имеет право только служебная уборка терминальных архивных процессов (ADR-0019) |
| Транзакция БД вокруг `await` внешнего сервиса | Нарушает §3.2 — блокировки держатся минуты вместо миллисекунд |
| `pg_advisory_lock` между шагами | Нарушает §3.3 — при падении воркера блокировка утечёт навсегда |
| Обработчик без `ProcessedOperation` | Нарушает §3.4 — повтор после ретрая продублирует эффект |
| `asyncio.sleep` для ожидания бизнес-события | Нарушает §3.6 — таймер должен быть durable-объектом в БД |
| Компенсация, которая может «откатиться назад» | Нарушает §3.5 — компенсация обязана быть необратимой |
| Схема принимает то, что движок не исполняет | Отказ на валидации лучше молчаливого полууспеха — см. ADR-0008 |
| Ограничение в схеме, которое никто не читает | Валидатор требует `max_iterations` — значит, код обязан его применять |
| Компенсация, которая не отменяет ничего | Резерв, не записанный в БД, отменить нечем — компенсация превращается в слово |
| План отката по колонке инстанса | Колонка стоит за шага в текущей итерации и ещё не учётна в нёй — §3.1 |
| Обёртка, переопределяющая повторяемость | Ошибка может быть повторяемой: если событие не изменилась, повтор не поможет |
| `except IntegrityError` без разбора причины | Нарушение внешнего ключа даёт ту же ошибку, что гонка за уникальным индексом |
| Тихий `except: pass` | Нарушает §3.7 — ошибка без события и без лога неотличима от успеха |
| Новый выбор без ADR | §8 — решение живёт только в чате, это недолговечно |
| Код без обновлённой документации | §8 — расхождение кода и документации является дефектом |
| `${DATABASE_URL}` в docker-compose | Compose берёт переменную из оболочки, и адрес хостовых скриптов уедет внутрь контейнера |
| Инструмент берёт «первое активное определение» | Активных определений может быть несколько — он молча проверит не то |
| Проверка правки в контейнерном дев-сервере | Bind-mount на Windows не доставляет события — сервис надо перезапустить |
| `pytest` при работающих воркерах | Воркер забирает аренду тестового инстанса, и тест видит чужой прогресс |
| «Убрать завершённые» как удаление строк | Журнал ссылается на инстанс с `RESTRICT`, а §3.1 запрещает терять историю — см. ADR-0017 |
| Объект из хука в зависимостях `useCallback` | Объект новый на каждом рендере, эффект срабатывает по кругу, и `testTimeout` не наступает |
| Тест лога, полагающийся на чужой `basicConfig` | Без явного `setLevel` он проходит в полном прогоне и падает в одиночном — и утверждает, что ничего не проверяет |
| Таблица, не попавшая в `TRUNCATE` фикстуры | Она копит мусор между тестами, и «ровно одна строка» превращается в «строка была и раньше» |
| Две переменные на один порт | Смена одной молча ломает вторую, и признак — пустые данные без ошибки |
| Адрес API, зашитый в браузер при сборке | Он перестаёт совпадать с портом публикации, и страница молчит |
| Правило инъекции, оставленное после сценария | Оно ломает следующий сценарий, и виноват окажется он, а не оставший |
| Два сценария, идущих одновременно | Правило на стенде одно: второй снимает поломку первого, и тот проходит «корректно» |
| Наблюдаемое состояние без действия | Показ заканчивается, и ожидаемое состояние со свидетельствами не проверяются никогда |
| Проверка, требующая глобальной чистоты | Проходит на пустом стенде и объявляет чужое состояние дефектом своего |
| Смена интервала опроса как повод перезагрузить | Удваивает запросы при каждом открытии страницы |
| Замороженные часы, которые всё равно идут | Окно проверки совпадает с опросом, и падает исправное поведение |
| Сон фиксированной длины вместо ожидания | Проверка на удачу: окно совпадает с периодом и падает при задержке |
| Пул без ограничения на файл | Часть воркеров не стартует, а прогон рапортует меньшим числом тестов |
| Повтор любого обращения при обрыве | Повтор создания даст два процесса, и проверка будет смотреть не на тот |
| Поиск элемента по тексту внешней секции | Обёртка содержит тот же текст, и находятся три кнопки вместо одной |
| Название карточки в `<header>` без роли | Скринридер видит подряд безымянные секции, и навигация по странице слепа |
| Слово внутреннего устройства в надписи | Читается как жаргон, а человек на экране слова «инстанс» не знает |
