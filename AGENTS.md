# AGENTS.md

Руководство для разработчиков и ИИ-агентов по работе с проектом **workflow-engine**.

Распределённый движок выполнения workflow с поддержкой долгих транзакций (long-running transactions) и компенсаций (Saga).

Стек: Python 3.13 (FastAPI, SQLAlchemy 2.0 async, Alembic, Pydantic v2), PostgreSQL 16, React 19 + TypeScript + Vite + Tailwind, Docker Compose, pytest, ruff, mypy.

## 2. Что это за проект

Движок исполняет **дефинишены workflow** — произвольные бизнес-процессы, описанные в JSON: шаги, ветвления, параллельные ветки, ожидания, компенсации.

Ключевая проблема, которую решает проект: **бизнес-транзакция живёт минуты и часы, а транзакция БД — миллисекунды**. Классический ACID не годится. Решение — **durable execution**: транзакция выражается не блокировкой строк, а последовательностью коротких коммитов, записанных в append-only журнал событий.

Демонстрационная предметная область: **заказ → резерв товара → оплата → отправление → подтверждение получения**, с компенсациями на каждом шаге.

## 3. Инварианты движка

Это жёсткие правила. Нарушение ломает корректность восстановления.

### 3.1. Журнал событий — единственный источник истины
- Таблица `workflow_events` — **append-only**. Никаких `UPDATE` и `DELETE` на ней.
- `seq` внутри инстанса строго монотонен, присваивается под блокировкой строки инстанса.
- Текущее состояние инстанса **выводится replay'ом журнала**. Произвольные `UPDATE workflow_instances SET status=...` запрещены — статус меняется только через запись события.
- Любая бизнес-операция, меняющая состояние инстанса, обязана в одной транзакции БД: (1) записать событие, (2) применить изменение. Если события нет — изменения не было.

### 3.2. Никаких долгих транзакций БД
- Транзакция SQLAlchemy `async with session.begin()` держится **только** на время одного короткого шага: запись события + изменение состояния.
- Запрещено держать транзакцию открытой во время `await` на внешний сервис, `asyncio.sleep`, ожидания таймера или между шагами workflow.
- Если кажется, что нужен «длинный транзакционный блок», — это сигнал, что нужен чекпоинт в журнале, а не блокировка.

### 3.3. Lease вместо распределённых блокировок
- Инстанс обрабатывается **ровно одним воркером** в любой момент, но воркер может умереть в любой момент.
- Координация: колонки `lease_owner`, `lease_expires_at`, `heartbeat_at` в `workflow_instances` + advisory-lock-free захват через `UPDATE ... WHERE lease_expires_at < now()`.
- Никогда не используй `pg_advisory_lock` и не держи блокировку дольше одной операции. Удержание блокировки между шагами — это утечка, которая вешает инстанс навсегда.
- Воркер обновляет heartbeat во время долгого шага. Если heartbeat не обновлялся дольше `lease_ttl_seconds` — lease считается протухшим, инстанс может быть перехвачен другим воркером.

### 3.4. Идемпотентность обязательна
- Доставка событий — **at-least-once**. Exactly-once не существует; имитируем его через идемпотентные обработчики.
- Каждый обработчик шага обязан быть безопасен при повторе: уникальный ключ операции + `INSERT ... ON CONFLICT DO NOTHING` в `processed_operations`.
- **Шаг не может быть повторён, если его эффект уже применён.** Проверка `ProcessedOperation` обязательна в начале обработчика, а не в конце.
- Обработчик не должен делать внешних необратимых действий (отправка email, списание реальных денег) без идемпотентного ключа, передаваемого наружу.

### 3.5. Saga и компенсации
- У каждого шага `action` есть компенсация `compensation`, объявленная в дефинишене явно.
- Компенсации выполняются **в обратном порядке** успешно завершённых шагов.
- Компенсация обязана быть **необратимой и идемпотентной**: её нельзя «компенсировать компенсацией» — она либо успешна, либо нет.
- Падение компенсации — не тихий сбой. Инстанс переходит в `COMPENSATION_FAILED`, компенсация ставится в очередь на повтор, в UI видно ручное разбирательство.
- Компенсация не должна падать из-за того, что компенсируемый шаг «кажется, не завершился». Проверяй факт через `step_runs`, а не через предположение.

### 3.6. Восстановление
- Воркер при старте обязан подобрать инстансы с протухшим lease и продолжить их с последнего durable-чекпоинта.
- Повторное выполнение шага после частичного сбоя должно быть безопасно (см. 3.4).
- Таймеры — durable-объекты в БД, а не `asyncio.sleep` в памяти. Переживают рестарт.

### 3.7. Наблюдаемость обязательна
- Каждое изменение состояния сопровождается событием в журнале. Нет события — нет изменения.
- Тайминги шагов пишутся в `step_runs` (`started_at`, `finished_at`) — без этого невозможно предъявить замеры.
- Ошибки логируются структурно, не через `print`. Никогда не логируются секреты и полные тела внешних запросов.

## 7. Стиль кода

### Python
- ruff, `line-length = 100`, target `py313`. Импорты сортируются автоматически.
- mypy: `disallow_untyped_defs = true` — **все** функции аннотированы.
- Асинхронность: `async def` для всего I/O. Блокирующие вызовы — только через `asyncio.to_thread`.
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов, `_`-префикс для приватных.
- Тип: `Decimal` для денег, никогда `float`. UUID для идентификаторов.
- Комментарии объясняют **почему**, а не **что**. Не комментировать очевидное.
- Docstring на русском для модулей и публичных функций ядра.

### React/TypeScript
- Функциональные компоненты, хуки, TypeScript `strict`.
- TanStack Query или собственная обёртка на SSE — выбор зафиксировать ADR'ом.
- Именование файлов компонентов — `PascalCase.tsx`, страниц — `lowercase.tsx` в `pages/`.
- Tailwind-классы, без CSS-in-JS. Тёмная тема — через CSS-переменные.

### Комментарии
- Комментарий объясняет **почему**, а не что. Пересказ строк кода — это шум, который
  устаревает раньше, чем код.
- Docstring у модуля — одна строка о назначении модуля. У функции — только если
  возвращаемое значение или побочный эффект неочевидны из сигнатуры.
- Норма — около одной строки комментария на десять строк кода, но только там, где
  причина не читается из самого кода.
- Ссылки на инварианты (`§3.2 AGENTS.md`) уместны там, где код рискует нарушить
  правило: они защищают от «оптимизации», ломающей корректность.

## 8. Правила ведения документации

- Вся документация на **русском языке**. README — тоже.
- Любое архитектурное решение с последствиями → ADR в `docs/adr/NNNN-короткое-описание.md`. Формат — Nygard: Context / Decision / Consequences (Positive / Negative / Neutral) / Alternatives considered / References.
- **Negative последствия обязательны и не могут быть пустыми.** Каждая отклонённая альтернатива приводится с её сильным доводом «за».
- Принятый ADR неизменяем. Новый контекст — новый ADR со строкой `Superseded by ADR-XXX` в старом.
- Схемы — Mermaid, исходники в `docs/diagrams/*.mmd`, вставлены в `.md` через ` ```mermaid `.
- Документация обновляется **в том же коммите**, что и код, который она описывает. Расхождение кода и документации — дефект.

## 9. Работа с git

Полное описание модели — `docs/GIT_WORKFLOW.md`. Здесь обязательный минимум.

### Модель веток

| Ветка | Откуда | Куда |
|---|---|---|
| `main` | — | только релизы, теги на каждой фазе |
| `develop` | `main` | интеграция текущей работы |
| `feature/<scope>-<описание>` | `develop` | `develop` через `--no-ff` |
| `fix/<описание>` | `develop` | `develop` через `--no-ff` |
| `release/<версия>` | `develop` | `main` + `develop`, тег |
| `hotfix/<описание>` | `main` | `main` + `develop`, тег |

- `main` и `develop` вечные. `git push --force` запрещён.
- Ветка удаляется после слияния: `git branch -d`.
- Один `feature` = одна фаза роадмапа (§11) или её логически завершённая часть.

### Формат коммита

```text
<type>(<scope>): <subject>

<body — почему, а не что>

Refs: #<задача>
```

- Один коммит — **одна область**. Изменения в нескольких областях дробятся на
  серию коммитов в порядке «снизу вверх»: `db` → `saga` → `api` → `test` → `docs`.
- Subject до 72 символов, строчные буквы, императив, без точки в конце.
- Тело обязательно, если причина не следует из subject.
- Типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `revert`.
- Области: `chore`, `docs`, `infra`, `db`, `journal`, `interpreter`, `lease`,
  `recovery`, `scheduler`, `saga`, `idempotency`, `registry`, `handlers`, `api`,
  `demo`, `frontend`, `test`, `chaos`, `perf`, `refactor`, `fix`.
- Файл, относящийся к двум областям, относится к более узкой
  (`app/engine/saga.py` → `saga`, не `engine`).
- Запрещены `wip`, `tmp`, коммиты без scope, смешивание кода и документации.
- Сообщения — на английском.

### Перед коммитом

Обязательно зелёный `make check`; для изменений кода — также `make test`.
Коммит с красными проверками не делается. Ослаблять правила, чтобы проверки
позеленели, запрещено.

### Релизы

Тег ставится на коммит слияния `release/*` в `main`. SemVer: новая
функциональность — минор, несовместимое изменение — мажор, фикс — патч.
Соответствие фаз и версий — `docs/GIT_WORKFLOW.md` §5.

## 10. Тестирование

- **Порог покрытия — 90% branch-покрытия.** Line-only считается обманом: `if`
  без `else` даёт 100% по строкам при непроверенной ветке.
- Порог задан в `engine/pyproject.toml` (`fail_under = 90`) и включается
  через `--cov-branch --cov-fail-under=90`. Обойти его нельзя молча —
  понижение порога или `# pragma: no cover` без объяснения в теле коммита
  означает ревью всего коммита.
- Из покрытия исключены `app/main.py` (точка входа), `alembic/` (миграции) и
  `app/models/base.py` (метаданные без логики).
- Маркеры pytest:
  | Маркер | Что покрывает | Нужна БД |
  |---|---|---|
  | без маркера | unit-тесты, чистая логика | нет |
  | `integration` | транзакции, журнал, lease, HTTP-слой на реальном PostgreSQL | да |
  | `chaos` | падение воркера, таймаут шага, недоступность сервиса | да |
- `integration` **входит** в порог: сервисный и HTTP-слой невозможно проверить
  без настоящей БД, и исключение маркера делало бы порог недостижимым.
  `chaos` не входит — эти тесты поднимают дополнительные процессы и медленны.
- Прогон без поднятой БД: `make test-fast` — только unit, без порога.
- Тест на каждый механизм ядра обязателен. Отсутствие теста на восстановление
  после падения воркера означает недоделанную фазу.
- Ошибка ловится тестом, который падает до исправления. Тест, который и так
  проходит, ничего не проверяет.

## 11. Roadmap по фазам

Каждая фаза — серия коммитов Conventional Commits. Ход работы фиксируется здесь.

### Фаза 0 — Техническое задание `[выполнено, релиз 0.1.0]`
- Каркас репозитория: `engine/`, `frontend/`, `docs/`, `docker-compose.yml`, `.env.example`.
- `README.md` с быстрым стартом.
- `AGENTS.md` (этот файл) + `docs/`: ARCHITECTURE, ENGINE, DATA-MODEL, API, DEVELOPMENT, OPERATIONS, GIT_WORKFLOW.
- ADR-0001 (стек) принят; ADR-0002…0006 зафиксированы в статусе `Proposed`.
- Mermaid-схемы: контекст, подсистемы, исполнение шага, восстановление, компенсации, машина состояний, ER.
- Gitflow и Conventional Commits, порог покрытия 90% (факт: 96% на каркасе).
- **Результат:** окружение поднимается одной командой, документация соответствует коду.
- Коммиты: 15 штук в `main`, теги `0.0.0` (правила) и `0.1.0` (Фаза 0).

### Фаза 1 — Эскизный проект `[выполнено, релиз 0.2.0]`
- Модель данных и миграции: `workflow_definitions`, `workflow_instances`, `workflow_events`, `step_runs`, `timers`, `processed_operations`, `compensation_log`.
- Схема дефинишена (JSON) + валидация структуры и семантики графа (нет циклов без `loop`, все компенсации разрешаются, все `next` существуют).
- ADR-0002…0006 приняты.
- **Результат:** схема БД создаётся миграцией, дефинишен валидируется, решения зафиксированы.
- Найдено при тестировании: члены `join` — входящие связи; их учёт как исходящих превращал fork/join в цикл.

### Фаза 2 — Технический проект: ядро `[выполнено, релиз 0.3.0]`
- `journal.py` — append-only журнал, последовательности, replay.
- `interpreter.py` — переходы состояний, ветвления, fork/join.
- `lease.py` — захват, heartbeat, освобождение.
- `scheduler.py` — durable-таймеры.
- `saga.py` — компенсации в обратном порядке, повторы, `COMPENSATION_FAILED`.
- `idempotency.py` — `ProcessedOperation`.
- `registry.py` — резолв обработчиков по import-path.
- `executor.py` — исполнение шага: транзакция закрывается до внешнего вызова.
- Unit + integration тесты на каждый механизм, chaos-тесты на падение воркера.
- **Результат:** движок исполняет дефинишен целиком и переживает падение воркера.
- Найдено при тестировании: раздельный `SELECT ... FOR UPDATE` и `UPDATE` захвата
  лишал второго воркера доступа к свободным инстансам; захват пачки оставлял
  воркера держать аренду на необработанных инстансах; удержание аренды после
  неудачного шага откладывало откат до истечения TTL.

### Фаза 3 — Технический проект: API и предметная область `[выполнено, релиз 0.4.0]`
- REST: дефинишены, инстансы, запуск, отмена, форсированное завершение.
- SSE `/api/stream` — live-обновления для UI.
- Обработчики демо-области: `inventory`, `payment`, `shipment`.
- Fault injection: `POST /api/chaos/*` — сломать шаг, сломать сервис, остановить аренду.
- Метрики: Prometheus-эндпоинт.
- **Результат:** движок управляется по HTTP, демонстрируется полный цикл с компенсацией.
- Найдено при тестировании: SSE отдавал пустой `instance_id` — идентификатор
  инстанса лежит в колонке события, а не в `payload`.

### Фаза 4 — Рабочий проект: фронтенд `[выполнено, релиз 0.5.0]`
- Каркас Vite + React + Tailwind, прокси `/api` на бэкенд.
- Dashboard: список инстансов с живым статусом через SSE.
- Страница инстанса: состояние из журнала, таймлайн шагов, журнал событий, компенсации.
- Редактор дефинишенов: JSON, валидация, запуск процесса с входными данными.
- Панель chaos-инъекций: сломать шаг, отключить сервис, остановить воркер.
- **Результат:** графический интерфейс закрывает весь сценарий демонстрации.
- Проверено вживую на Docker: полный проход, компенсация по инъекции, смена владельца аренды, поток SSE, метрики.

### Фаза 5 — Рабочий проект: отладка и испытания `[выполнено, релиз 0.6.0]`
- Отладка каждого механизма (автономная → комплексная).
- Контрольный пример: сбой на шаге оплаты → автоматический откат.
- Тесты: unit, integration, chaos (падение воркера, таймаут шага, недоступность сервиса).
- Замеры: throughput, latency по шагам, время компенсации.
- `engine/scripts/`: `seed` (наполнение), `smoke` (сквозная проверка), `load` (замеры).
- Методика замеров зафиксирована в ADR-0007, результаты — в `docs/BENCHMARKS.md`.
- **Результат:** измеримые характеристики, подтверждённая устойчивость. 300 инстансов:
  1 воркер — 2.8 инстанса/с, 2 — 5.4, 4 — 10.3; шаг ~20 мс, компенсация ~41 мс. (замеры на 1.2.0; перезамер на 1.2.1 запланирован)
- Найдено при испытаниях:
  - `wait_before_seconds` из дефинишена нигде не применялся — `interpreter.wait_before()`
    не вызывался, и процесс с ожиданием проходил мгновенно;
  - сработавший таймер не будил инстанс: `claim_due()` вызывался, но результат
    выбрасывался, а `notify_fired()` не вызывался нигде в приложении — инстанс
    навсегда зависал в `WAITING`;
  - спящий `WAITING`-инстанс попадал в `claim_next` и, оставаясь самым старым,
    блокировал очередь: воркер брал его снова, пока тот не просыпался;
  - отметка `fired` и событие `TIMER_FIRED` шли разными транзакциями — падение
    воркера между ними оставляло инстанс спящим навсегда.

### Фаза 6 — Внедрение `[выполнено, релиз 1.0.1]`
- Полный комплект `docs/` актуален и соответствует коду.
- `README.md` — быстрый старт с нуля.
- Акт внедрения: `docs/DEPLOYMENT-ACT.md`.
- Замеры пересняты на машине без посторонней нагрузки: разброс между
  прогонами упал с 20% до единиц процентов.
- Финальный прогон всех проверок: 383 теста, покрытие branch 93.39%,
  `smoke` 12 из 12.
- **Результат:** проект готов к сдаче.
- Найдено при внедрении:
  - ветка `next.on_failure` не исполнялась: исполнитель записывал решение
    интерпретатора, но не переносил его в журнал, поэтому процесс уходил в
    откат вместо объявленной ветки;
  - **отмена инстанса не выполняла компенсацию**: запрос отмены писал
    терминальное событие, и воркер завершал процесс с выполненными шагами —
    резерв или списание оставались в силе навсегда;
  - компенсация не была идемпотентной: ключ операции складывался, но не
    использовался, а падение воркера между компенсацией и её фиксацией
    приводило к повторному возврату средств;
  - ветки `fork` / `join` принимаются схемой и валидатором, но не
    исполняются — ограничение зафиксировано в акте внедрения;
  - тесты и замеры требуют разных состояний стенда: тесты делают `TRUNCATE`,
    а работающий воркер держит блокировки, и вместе они дают
    взаимоблокировку.

### Фаза 8 — Настоящая предметная область и наблюдаемость `[выполнено, релизы 1.2.0 и 1.2.1]`
- **Компенсация отменяет данные.** Раньше обработчики возвращали словари и
  ничего не меняли: резерв не существовал, отменять было нечего. Теперь
  резервирование, списание и отправление пишутся в БД, компенсации отменяют эти
  записи, и откат проверяется по данным.
- **Атомарная идемпотентность.** Проверка ключа, эффект и отметка идут одной
  транзакцией. Раньше окно между проверкой в движке и отметкой после эффекта
  давало повторное применение — безобидно, пока обработчик ничего не делал.
- **Контекст компенсации.** Компенсация вызывалась как `handler(None)` и не
  знала, что отменяет.
- **Ограничение остатка.** `reserved <= available` плюс миграция: заказ больше
  остатка падает как шаг.
- **Страж образца в редакторе.** Опечатка в имени обработчика показывалась
  только при попытке сохранить определение.
- **Интерфейс:** экран состояния с тревогами по таблице из OPERATIONS.md,
  граница ошибок, поиск и сортировка инстансов, пресеты шагов в панели инъекций,
  валидация определения до сохранения.
- **Результат:** откат доказывается данными, границы движка остаются
  задокументированными, интерфейс показывает механику.
- Найдено при доработке:
  - компенсация получала `None` вместо контекста;
  - обработчики ничего не писали, а документация утверждала обратное;
  - `IntegrityError` от нарушения внешнего ключа проглатывался как гонка за
    уникальным ограничением: откат тихо отменял бы применённый эффект;
  - в образце определения — опечатка в обработчике, имя, совпадающее с
    seed, и несуществующий артикул;
  - `session.get` искал товар по первичному ключу вместо артикула;
  - тест `test_compensation_handlers_are_idempotent_noops` утверждал, что
    компенсации ничего не делают.
  - план отката строился по колонке инстанса, а по replay'"у: колонка стоит за шага в текущей итерации и ещё не учётна в нёй, и план отката выродался пустым, хотя резерв уже занят;
  - `retryable` терялся надвух этапах: `_invoke` обёртывал ошибку в `StepFailed(retryable=True)`, и недостатка товара не повторялась — отказ по правилу срашал в `max_attempts` раз;
  - отказ без компенсации писал `INSTANCE_COMPENSATED`, а повтор отката менял статус без события — `replay` весгда отдау и не стал бы повторена.

### Фаза 7 — Наблюдаемость и честные границы `[выполнено, релиз 1.1.0]`
- **Циклы исполняются.** Счётчик `max_iterations` требовался валидатором, но не
  читался кодом: определение с циклом проходило проверку и зависало навсегда.
  Счётчик живёт в `InstanceState` и растёт из журнала; по достижении предела
  пишется `LOOP_EXHAUSTED` и процесс уходит в компенсацию.
- **Параллельные ветки отвергаются валидатором.** Раньше определение с `fork`
  сохранялось, а процесс выполнял префикс графа и отчитывался об успехе.
  Решение и его цена — ADR-0008.
- **Граф шагов на странице инстанса:** послойная раскладка, обратные рёбра
  цикла, цвет узла по фактическому состоянию, полоса фактического порядка
  отката.
- **Наблюдаемость:** payload событий раскрывается, ожидание показывает
  отсчёт по дате из `TIMER_SCHEDULED`, панель аренды и heartbeat, время
  последнего события потока.
- **19 тестов фронтенда:** раскладка схемы, раскраска узлов, группировка
  аренд. Vitest настроен — до этого скрипт `test` был без единого теста.
- **Результат:** границы движка перестали быть неожиданностью для
  пользователя; интерфейс показывает механику, а не только статусы.
- Найдено при доработке:
  - `max_iterations` нигде не использовался: счётчик был обязателен в
    валидаторе и отсутствовал в движке;
  - параллельные ветки проходили валидацию и давали молчаливый полууспех;
  - интерфейс получал ссылку на определение без `id`, из-за чего схему шагов
    было не загрузить;
  - в списке инстансов не отдавался `heartbeat_at`, из-за чего простой и
    молчание воркера были неразличимы.

### Фаза 9 — Разбор стенда: дефекты, производительность, наблюдаемость `[в работе, ветка fix/audit-findings]`
Разбор стенда на живых данных, а не по коду. Найдено шесть фаз, каждая с
тестом, падающим до исправления.
- **Дефекты.** `update()` слал весь объект редактора вместо `{definition, is_active}`
  и получал 422; `mark_applied` глотал нарушение внешнего ключа, выдавая его за
  гонку за уникальным индексом; правило инъекции в режиме `once` не отбиралось;
  редьюсер SSE обновлял состояние вне `set`, теряя события при пакетном обновлении;
  метрики страницы не различали ошибку и «метрик нет».
- **Производительность.** Четыре индекса под горячие пути: на 60 000 событий
  разбор журнала перешёл с 3489 буферов на 204, сортировка ушла совсем.
  Пул соединений уменьшен до 5+5 с таймаутом меньше TTL. Поток событий больше
  не прогонывает всю историю на каждом подключении: курсор по времени,
  событие с `id:`, опрос раз в секунду вместо heartbeat'а. Страница инстанса
  не дёргала пять запросов на каждое событие.
- **Наблюдаемость.** Четыре метрики были объявлены, но не писались: теперь
  подключены к точкам, где случается факт. `Content-Type` объявлял OpenMetrics
  при теле в формате Prometheus — строгий скрайпер отверг бы весь ответ.
  `CycleResult.lease_lost` был объявлен, но не читался.
- **Доступность.** Ошибки не объявлялись скринридеру, заголовки таблиц теряли
  связь с колонками, узлы графа шагов были доступны только мышью.
- **Тесты фронтенда.** Разбор ошибок бэкенда, сборка запросов, подписи
  состояний: 35 → 54 теста. Найдено: неразбираная дата попадала в журнал
  как «Invalid Date».
- **Контракт и чистка.** В трёх местах текст был повреждён кодировкой и
  читался как знаки вопроса.

Не сделано сознательно: порог покрытия фронтенда не задан — для этого нужен
`@vitest/coverage-v8`, а новая зависимость в проект не вносилась без решения.

Найдено при разборе:
- SSE начинал соединение с эпохи и слал всю историю журнала: на каждое
  подключение приходились все события работы стенда;
- частота опроса потока была случайно равна интервалу heartbeat;
- `step_run` после коммита протухает, и чтение его атрибутов из асинхронного
  кода кончалось `MissingGreenlet` — длительность пришлось считать по
  границам, сохранённым в локальных переменных;
- `INSTANCE_STARTED` не входит в публикуемые события, и тест на поток
  проверял событие, которое поток никогда не отдаёт.

## 12. Частые ошибки

| Ошибка | Почему это неверно |
|---|---|
| `UPDATE workflow_instances SET status` напрямую | Нарушает §3.1 — состояние только через журнал |
| Транзакция БД вокруг `await` внешнего сервиса | Нарушает §3.2 — блокировки держатся минуты вместо миллисекунд |
| `pg_advisory_lock` между шагами | Нарушает §3.3 — при падении воркера блокировка утечёт навсегда |
| Обработчик без `ProcessedOperation` | Нарушает §3.4 — повтор после ретрая продублирует эффект |
| `asyncio.sleep` для ожидания бизнес-события | Нарушает §3.6 — таймер должен быть durable-объектом в БД |
| Компенсация, которая может «откатиться назад» | Нарушает §3.5 — компенсация обязана быть необратимой |
| Схема принимает то, что движок не исполняет | Отказ на валидации лучше молчаливого полууспеха — см. ADR-0008 |
| Ограничение в схеме, которое никто не читает | Валидатор требует `max_iterations` — значит, код обязан его применять |
| Компенсация, которая не отменяет ничего | Резерв, не записанный в БД, отменить нечем — компенсация превращается в слово |
| План отката по колонке инстанса | Колонка стоит за шага в текущей итерации и ещё не учётна в нёй — §3.1 |
| Обёртка, переопределяющая повторяемость | Ошибка может быть повторяемой: если событие не изменилась, повтор не поможет |
| `except IntegrityError` без разбора причины | Нарушение внешнего ключа даёт ту же ошибку, что гонка за уникальным индексом |
| Тихий `except: pass` | Нарушает §3.7 — ошибка без события и без лога неотличима от успеха |
| Новый выбор без ADR | §8 — решение живёт только в чате, это недолговечно |
| Код без обновлённой документации | §8 — расхождение кода и документации является дефектом |
