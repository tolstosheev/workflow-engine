# Workflow Engine

Распределённый движок выполнения workflow с поддержкой долгих транзакций
(long-running transactions) и компенсаций (Saga).

Движок исполняет бизнес-процессы, описанные в JSON: последовательные шаги,
ветвления, параллельные ветки, ожидания и компенсации. Ключевая идея — транзакция
уровня бизнес-процесса не выражается блокировкой строк, а набирается из
последовательности коротких коммитов, записанных в append-only журнал событий.
Поэтому процесс может жить минуты и часы, переживать падение воркера и
перезапускаться с последнего durable-чекпоинта.

---

## Возможности

- **Долгие транзакции.** Транзакция БД открыта на один короткий шаг; состояние
  инстанса восстанавливается replay'ом журнала событий.
- **Saga и компенсации.** У каждого шага объявлена компенсация; откат идёт в
  обратном порядке, ошибка компенсации переводит инстанс в `COMPENSATION_FAILED`.
- **Отказоустойчивость.** Воркеры конкурируют за инстансы через
  `SELECT ... FOR UPDATE SKIP LOCKED` и lease с heartbeat — падение воркера не
  теряет и не дублирует работу.
- **Идемпотентность.** Доставка at-least-once компенсируется таблицей
  `processed_operations`: уже применённый эффект не применяется дважды.
- **Durable-таймеры.** Ожидания хранятся в БД, а не в памяти процесса, поэтому
  переживают рестарт.
- **Наблюдаемость.** Полный журнал событий с раскрытием содержимого, тайминги
  шагов, схема графа с цветом шагов по фактическому состоянию, обратный отсчёт
  до ожидания, панель аренды и heartbeat, экран состояния системы с тревогами,
  live-обновление интерфейса через SSE, метрики Prometheus.
- **Настоящая предметная область.** Резерв, списание и отправление пишутся в
  БД, и компенсации отменяют эти записи: после отката остаток на складе
  возвращается к исходному, платёж переходит в `REFUNDED`. Откат виден в
  данных, а не только в журнале.
- **Честные границы.** Параллельные ветки `fork` / `join` объявлены в формате,
  но не исполняются: определения с ними отвергаются при сохранении с понятным
  сообщением. Решение и его цена — [ADR-0008](docs/adr/0008-parallelnye-vetki-otkaz.md).

## Быстрый старт

### Docker Compose (рекомендуется)

```bash
cp .env.example .env
docker compose up -d --build
```

Поднимется:

| Сервис | Адрес | Назначение |
|---|---|---|
| `db` | `localhost:5434` | PostgreSQL |
| `api` | http://localhost:8000 | REST API, документация OpenAPI на `/docs` |
| `worker`, `worker-2` | — | Две реплики воркера исполнения |
| `frontend` | http://localhost:5173 | Интерфейс |

Миграции применяет сервис `migrate` до старта API и воркеров.

```bash
docker compose logs -f worker      # логи исполнения
docker compose down                # остановить
```

### Наполнение демонстрационными данными

```bash
cd engine && python -m scripts.seed && cd ..
```

Скрипт загружает определение заказа с компенсациями и остатки склада.
Идемпотентен: повторный запуск обновляет строки, а не падает.

### Занятые порты

Порт занят другой системой — переопределяйте через `.env` (файл не
отслеживается git):

```bash
API_PORT=8001
VITE_API_URL=http://localhost:8001
```

Тот же адрес передаётся скриптам: `make smoke API_URL=http://localhost:8001`.

Контейнер `frontend` не поднимется, если порт 5173 уже занят работающим
локальным `npm run dev`. Это ожидаемо: локальный Vite отдаёт фронтенд, а из
контейнера берут только API и воркеры.

### Локальная разработка

```bash
cd engine
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env

docker compose up -d db            # только БД
alembic upgrade head
uvicorn app.main:app --reload      # терминал 1
python -m app.worker               # терминал 2
```

```bash
cd frontend
npm install
npm run dev
```

```bash
make check              # ruff + ruff format + mypy + eslint + tsc

```

## Сквозная проверка и замеры

```bash
make seed               # демонстрационные данные
make smoke              # контрольный пример: полный проход и откат
make bench              # throughput, длительность шагов, время компенсации
make chaos-demo         # только откат, для показа на защите
```

`make smoke` проверяет поведение и возвращает ненулевой код при расхождении,
поэтому пригоден для CI. `make bench` меряет скорость на живой системе;
методика — в [ADR-0007](docs/adr/0007-metodika-zmerov.md), результаты — в
[`docs/BENCHMARKS.md`](docs/BENCHMARKS.md).

| Скрипт | Что делает |
|---|---|
| `scripts/seed.py` | определение workflow с компенсациями и остатки склада |
| `scripts/smoke.py` | полный проход, сбой на оплате, откат, проверки журнала |
| `scripts/load.py` | нагрузочный прогон и три вида замеров |

## Демонстрационная предметная область

Заказ → резерв товара → списание средств → создание отправления → подтверждение
получения. У каждого шага есть компенсация: отмена резерва, возврат средств,
отмена доставки. Контрольный сценарий — сбой на шаге оплаты: движок сам
откатывает выполненные шаги в обратном порядке.

Разработка разделена на фазы в разделе «Roadmap» файла [`AGENTS.md`](AGENTS.md).
