# Gitflow и правила коммитов

Проект использует классический Gitflow и Conventional Commits. Документ
описывает модель веток, допустимые области коммитов и требования к сообщениям.

---

## 1. Ветки

| Ветка | Откуда | Куда | Содержимое | Срок жизни |
|---|---|---|---|---|
| `main` | — | — | только релизы | вечная |
| `develop` | `main` | — | вся текущая работа | вечная |
| `feature/<scope>-<описание>` | `develop` | `develop` | одна фича или часть фазы роадмапа | до слияния |
| `fix/<описание>` | `develop` | `develop` | исправление дефекта | до слияния |
| `release/<версия>` | `develop` | `main` + `develop` | только фиксы релиза | до слияния |
| `hotfix/<описание>` | `main` | `main` + `develop` | срочное исправление в релизе | до слияния |

Правила:

- `main` и `develop` не перезаписываются. Команда `git push --force` запрещена.
- `feature/*` и `fix/*` сливаются в `develop` ключом `--no-ff`: коммиты внутри
  ветки — это история работы, и она сохраняется.
- `release/*` создаётся, когда `develop` достиг состояния релиза. Внутри
  `release/*` новые фичи не добавляются — только фиксы и документация.
- После слияния рабочая ветка удаляется: `git branch -d <ветка>`.
- Один `feature` соответствует одной фазе из роадмапа [`../AGENTS.md`](../AGENTS.md)
  §9 или её логически завершённой части.

### Цикл разработки

```bash
git switch develop
git pull --ff-only
git switch -c feature/lease-atomik-zahvat

# ... работа ...

make check          # проверки обязательны перед коммитом
git add -A
git commit
git push -u origin feature/lease-atomik-zahvat
# → Pull Request в develop, после ревью:
git switch develop
git merge --no-ff feature/lease-atomik-zahvat
git branch -d feature/lease-atomik-zahvat
```

### Цикл релиза

```bash
git switch develop
git switch -c release/0.2.0
# только фиксы
git switch main
git merge --no-ff release/0.2.0
git tag -a 0.2.0 -m "Фаза 1: модель данных и валидация дефинишенов"
git switch develop
git merge --no-ff release/0.2.0
git branch -d release/0.2.0
```

### Цикл hotfix

```bash
git switch main
git switch -c hotfix/lease-protyaka
# фикс
git switch main
git merge --no-ff hotfix/lease-protyaka
git tag -a 0.2.1 -m "hotfix: lease не продлевается на длинном шаге"
git switch develop
git merge --no-ff hotfix/lease-protyaka
git branch -d hotfix/lease-protyaka
```

## 2. Области коммитов

Каждый коммит относится **ровно к одной области**. Изменения, затрагивающие
несколько областей, дробятся на серию коммитов — см. §4.

| Scope | Что коммитится |
|---|---|
| `chore` | Каркас, конфиги, `.gitignore`, `Makefile` — без функциональности |
| `docs` | Только `docs/**`, `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, ADR |
| `infra` | `Dockerfile`, `docker-compose.yml`, CI |
| `db` | SQLAlchemy-модели, миграции Alembic |
| `journal` | Журнал событий, последовательности, replay |
| `interpreter` | Переходы состояний, ветвления, fork/join |
| `lease` | Захват, heartbeat, освобождение lease |
| `recovery` | Подбор протухших инстансов, продолжение с чекпоинта |
| `scheduler` | Durable-таймеры |
| `saga` | Компенсации, Saga Log, `COMPENSATION_FAILED` |
| `idempotency` | `processed_operations`, защита от повторов |
| `registry` | Резолв обработчиков по import-path |
| `handlers` | Обработчики шагов |
| `api` | Роутеры, схемы Pydantic, SSE |
| `demo` | Предметная область: inventory, payment, shipment |
| `frontend` | React SPA |
| `test` | Тесты |
| `chaos` | Тесты отказоустойчивости |
| `perf` | Оптимизация с сохранением поведения |
| `refactor` | Перестройка без изменения поведения |
| `fix` | Исправление дефекта (scope уточняет область) |

Файл, который можно отнести к двум областям, относится к более узкой:
`app/engine/saga.py` → `saga`, а не `engine`.

## 3. Формат сообщений

```text
<type>(<scope>): <subject>

<body — почему, а не что>

Refs: #<задача>
```

- Первая строка — до 72 символов, строчные буквы, императивная форма
  (`add`, не `added`), без точки в конце.
- Тело обязательно, если причина изменения не следует из subject. Тело
  объясняет **зачем**, а не перечисляет строки diff.
- Несовместимое изменение: `!` после scope и раздел `BREAKING CHANGE:` в теле.

Допустимые типы: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`,
`ci`, `chore`, `revert`.

Примеры:

```text
feat(lease): захват инстанса атомарным UPDATE с условием на истёкший lease

Конкуренты не блокируют друг друга: UPDATE возвращает 0 строк проигравшему,
и он переходит к следующему кандидату. Без условия на lease_expires_at
второй воркер перехватил бы инстанс посреди исполнения шага.
```

```text
fix(saga): компенсация падает, если компенсируемый шаг не найден в step_runs

Проверка строилась на предположении, что шаг в журнале есть. После падения
воркера между записью события и коммитом step_runs такая строка отсутствует —
компенсация уходила в COMPENSATION_FAILED вместо откатa резерва.
```

```text
test(chaos): воркер убит посреди шага — инстанс подхвачен другим

Инстанс переходит на второй воркер после истечения TTL lease и продолжает
с последнего чекпоинта, не дублируя уже применённый эффект шага.
```

## 4. Дробление изменений

Одна фича почти всегда затрагивает несколько областей. Пример: переход
инстанса в компенсацию требует изменений в `db`, `saga`, `api` и `docs`.
Разбивается на четыре коммита в порядке «снизу вверх» — так, чтобы каждый
коммит оставлял репозиторий в согласованном состоянии:

```text
db(saga):      таблица compensation_log с журналом попыток компенсаций
saga:          выбор компенсаций в обратном порядке по step_runs
api(saga):     эндпоинт ручного перезапуска компенсации
docs(saga):    описать переход в COMPENSATION_FAILED
```

Порядок «снизу вверх» не случаен: коммит с тестами идёт последним в своей
области, когда код уже на месте.

## 5. Теги и версии

Тег ставится на коммит слияния `release/*` в `main`. Версионирование —
Semantic Versioning:

| Изменение | Пример версии |
|---|---|
| Несовместимое изменение формата дефинишена или API | `1.0.0` → `2.0.0` |
| Новая функциональность обратно совместима | `0.1.0` → `0.2.0` |
| Исправление дефекта | `0.2.0` → `0.2.1` |

Релизы по фазам роадмапа:

| Тег | Содержание |
|---|---|
| `0.0.0` | Пустой репозиторий: зафиксированы правила |
| `0.1.0` | Фаза 0 — каркас, документация, окружение |
| `0.2.0` | Фаза 1 — модель данных, миграции, валидация дефинишена |
| `0.3.0` | Фаза 2 — ядро: журнал, интерпретатор, lease, Saga |
| `0.4.0` | Фаза 3 — REST/SSE API, демо-область, chaos |
| `0.5.0` | Фаза 4 — фронтенд |
| `0.6.0` | Фаза 5 — отладка, испытания, замеры |
| `1.0.0` | Фаза 6 — внедрение |
| `1.0.1` | Исправление фазы 6: подтвержденое оприсание |
| `1.1.0` | Фаза 7 — исполняемые циклы, граф процесса, отказ паралельных веткиой |
| `1.2.0` | Фаза 8 — предметная область работает с данными, обратоковой компенсацией |
| `1.2.1` | Повтор: откат по журналу, постоянные ошибки без повторов, `INSTANCE_FAILED` |

## 6. Обязательные проверки

Перед каждым коммитом:

```bash
make check   # ruff check, ruff format --check, mypy, eslint, tsc
make test    # pytest с порогом покрытия 92%
```

Коммит с красными проверками не делается. Исключение — `docs`-коммиты:
для них достаточно `make check`, покрытие документация не меняет.
