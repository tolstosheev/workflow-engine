# ADR-0012: Метрики в multiprocess-режиме Prometheus

**Статус**: Accepted
**Дата**: 2026-10-11
**Область**: наблюдаемость, эксплуатация

## Контекст

`app/metrics.py` создаёт `CollectorRegistry()` на процесс, а единственная точка
экспорта — `/metrics` в процессе API. Воркер — отдельный процесс, и всё, что он
записывает в счётчики, там и остаётся.

На живом стенде это видно буквально: `workflow_instances_created_total` растёт
(его пишет API при создании инстанса), а `workflow_lease_acquired_total` равен
нулю, и `workflow_step_duration_seconds_count` не появляется вовсе — хотя
`LEASE_ACQUIRED` и `STEP_DURATION` подключены и работают в процессе воркера.

Тесты этого не ловят: они проверяют счётчик в том же процессе, где он растёт.
Дефект виден только на стенде, где два процесса.

Источник метрик у API один — база, а у воркера — факт исполнения шага. Значит,
экспорт должен собирать значения из обоих процессов, не смешивая их смысл.

## Решение

Включить штатный multiprocess-режим `prometheus_client` через переменную
окружения `PROMETHEUS_MULTIPROC_DIR`, общий том между API и воркерами.
Каждый процесс пишет значения в файлы этого каталога, а `/metrics` собирает их
все через `MultiProcessCollector`.

Режим агрегации выбирается по смыслу метрики, а не по умолчанию:

| Метрики | Источник | Режим | Почему |
|---|---|---|---|
| `INSTANCES_TOTAL`, `LEASE_ACQUIRED`, `LEASE_LOST` | события в процессах | сумма | счётчики событий складываются по смыслу |
| `STEP_DURATION` | прогоны шагов в воркерах | сумма | распределение собирается из всех прогонов |
| `INSTANCES_BY_STATUS`, `STEPS_BY_RESULT`, `COMPENSATIONS_BY_RESULT` | выборка из БД | `mostrecent` | все процессы считают одно и то же по общей базе; сумма задвоила бы значение |

`mostrecent` выбран по измеренному поведению: при режиме по умолчанию gauge
разворачивается в серии с меткой `pid`, и запрос вида
`workflow_instances{status="RUNNING"}` перестаёт работать — появляется
несколько рядов. `mostrecent` отдаёт одну серию без `pid`.

Воркер на выходе вызывает `mark_process_dead(pid)`: файлы упавшего процесса
иначе остаются в каталоге навсегда, и счётчики мёртвого воркера продолжают
значения.

## Последствия

### Положительные

- Метрики исполнения — захваты аренды, потери аренды, длительности шагов —
  видны в `/metrics` и собираются скрайпером.
- Вид экспозиции для метрик из БД не меняется: одна серия, без `pid`.
- Добавление счётчика в воркере больше не требует ничего, кроме самой строки.

### Отрицательные

- Нужен общий том между API и воркерами. Без `PROMETHEUS_MULTIPROC_DIR`
  поведение прежнее: счётчики воркера снова не видны. Поэтому проверка на
  стенде обязательна после изменения схемы запуска.
- Каталог multiproc растёт по мере работы: файлы создаются на каждое значение.
  Очистка — либо вызов `mark_process_dead`, либо периодическое удаление
  каталога при перезапуске (описано в `OPERATIONS.md`).
- `mostrecent` полагается на время изменения файлов: если реплика API молчала,
  её прошлое значение остаётся в графике, пока не отвечает другая. Для
  одиночного API (текущая схема развёртывания) это незаметно, при нескольких
  репликах — повод смотреть на свежесть скрапинга.
- `pid: host` у воркеров обязателен со хоздайствой доменной PID-пространства: иначе отправление воркера теперь повторно по сети, а на Windows такой режим не допустим на всех платформах.
- Метрики процесса воркера, не выраженные в счётчиках (логи, трассировки),
  по-прежнему не собираются: это не Prometheus.

### Нейтральные

- Тесты движка продолжают работать без переменной окружения: без неё
  `prometheus_client` остаётся в однопроцессном режиме.
- Состав метрик не меняется, меняется только способ их доставки.

### Найдено при внедрении

Оба предположения вызывались два ошибки, обе издали
в реестре для повторного склепывания.

**Две ряда в реестре.** Сборка файлов в общий реестре вела и собственные
значения одного процесса: имена файла выбираются по pid, а
два воркера в разных контейнерах имеют pid 1 и пишут в один файл. Замер
ского смещения пропало без следа: позамеру 32 вместо вместо 12.
Измерение нашего предоставляет работу воркера нельзя именно по
замеру вместа, и такая потеря счётчика выглядела бы неожидаемой.

**Одна серия была проверена по целочке.** Файлы в
общем каталоге накапливаются на старте композиции и не удаляются:
при смене режима агрегата старые файлы от предыдущего режима.

## Рассмотренные альтернативы

1. **Считать метрики воркера из БД в процессе API.** Длительность шага
   берётся из `step_runs` без потери точности, но счётчики захвата и потери
   аренды восстановить нельзя: захват не оставляет события в журнале. Придётся
   либо отказаться от них, либо ввести событие захвата — а это изменение
   журнала, то есть инварианта §3.1, ради косметики метрик.
2. **Отдельный эндпоинт метрик у воркера.** Воркер перестаёт быть просто
   циклом и становится сетевым сервисом: порт, запуск, остановка, второй
   адрес для скрайпера на каждой реплике. Дороже, чем требуется задаче.
3. **Оставить как есть и описать ограничение в документации.** Самое
   дешёвое, но две метрики всегда нулевые: график выглядит работающим и вводит
   в заблуждение — ровно тот случай, ради которого метрики и существуют.
