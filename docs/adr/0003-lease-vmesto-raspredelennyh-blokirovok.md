# ADR-0003: Lease вместо распределённых блокировок

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Deciders** | команда проекта |

## Context

Требуется, чтобы инстанс обрабатывался **ровно одним** воркером в любой
момент, но воркер при этом может умереть в любой момент.

Это противоречие разрешается двумя разными механизмами:

| Механизм | Снимает ли взаимоблокировку | Освобождается ли при падении |
|---|---|---|
| Распределённая блокировка (advisory lock, Redlock) | Да | **Нет** — требует внешнего процесса для освобождения |
| Lease с временем истечения | Да | Да — по истечении TTL |

Формально подходят оба, и разница проявляется только при сбое.

## Decision

Координация строится на lease: три колонки в `workflow_instances`
(`lease_owner`, `lease_expires_at`, `heartbeat_at`), атомарный захват через
`UPDATE ... WHERE lease_expires_at IS NULL OR lease_expires_at < now()`,
подбор кандидатов через `SELECT ... FOR UPDATE SKIP LOCKED`.

Воркер продлевает lease во время исполнения шага. Условие освобождения
`WHERE lease_owner = :worker_id` обязательно.

`pg_advisory_lock` не используется нигде.

## Consequences

**Positive:**

- Падение воркера освобождает инстанс автоматически по истечении TTL. Не
  нужна ни процедура восстановления, ни внешний координатор.
- `SKIP LOCKED` снимает конкуренцию: воркеры не блокируют друг друга, а
  пропускают занятые строки и берут следующую.
- Состояние координации находится в той же БД и в той же транзакции, что и
  остальное состояние. Нет второй системы, расходящейся с первой.
- Работает на обычном PostgreSQL: не нужен ZooKeeper, etcd или иной сервис
  координации.

**Negative:**

- **Асимметрия сбоя.** Нет способа отличить «воркер выполняет долгий шаг» от
  «воркер мёртв». Lease с истечением выбирает TTL как компромисс: он должен
  перекрывать максимальную длительность шага. Слишком малый TTL вызывает
  двойное исполнение; слишком большой — долгий простой после падения.
- **Разделение Brain.** Сеть может разорваться так, что старый воркер считает
  себя владельцем, а новый уже перехватил инстанс. Защита — условие по
  `lease_owner` при записи: нулевое число затронутых строк означает потерю
  lease, и воркер обязан прекратить работу с инстансом. Цена — часть работы
  воркера может быть потеряна (он её не запишет), но не продублирована.
- **Clock skew.** Решение об истечении принимает сервер БД (`now()`), поэтому
  рассинхронизация часов воркеров не влияет на захват. Но сам heartbeat
  отправляется с часов воркера, и большой сдвиг часов искажает время
  последнего продления.
- `UPDATE` с условием на истёкший lease при высокой конкуренции создаёт
  больше откатов, чем `pg_advisory_lock`: часть попыток захвата неизбежно
  проигрывает.

## Alternatives considered

**`pg_advisory_lock` на хеш идентификатора инстанса.** Для: встроен в
PostgreSQL, не требует дополнительных колонок и миграций, работает без
дополнительного кода — `pg_try_advisory_lock` возвращает ложь вместо
ожидания. Для коротких операций это действительно проще и дешевле.
Против: блокировка **не освобождается при падении сессии в ходе транзакции,
и её нельзя освободить по времени**. Если воркер упал между шагами, инстанс
заблокирован навсегда — до ручного вмешательства. Требование «переживает
падение воркера» при этом не выполняется в принципе. Кроме того,
управление сессионными advisory-блокировками требует выделенного соединения на
весь срок аренды, что противоречит модели коротких транзакций.
Не выбрано: не переживает сбой — это блокирующий дефект, а не компромисс.

**Redlock поверх Redis.** Для: явное время истечения TTL на стороне Redis,
популярная реализация с библиотеками для всех языков, понятная семантика
аренды с возможностью продления.
Против: вторая система с собственным отказом. Сложность алгоритма Redlock
при недостаточной синхронизации часов даёт ситуации, где два воркера считают
себя владельцами одновременно — ровно та проблема, которую lease в
PostgreSQL решает серверными часами и одной транзакцией. Значимость TTL в
Redis (часто порядка сотен миллисекунд) плохо подходит для многосекундных
шагов. Не выбрано: плата за вторую систему не даёт выигрыша.

**Очередь на `SELECT ... FOR UPDATE SKIP LOCKED` без lease.** Для: ровно та же
БД и тот же механизм блокировок строк, что и сейчас, но без трёх колонок и
heartbeat — заметно проще.
Против: блокировка строки удерживается до конца транзакции. Если транзакция —
это только выбор задачи, а исполнение шага идёт вне неё, то после commit
строка разблокируется и второй воркер возьмёт тот же инстанс немедленно.
Чтобы этого избежать, транзакцию пришлось бы продлить на всё исполнение шага —
то есть вернуться к долгой транзакции из ADR-0002. Lease совмещает обе задачи:
строка заблокирована на время захвата, а «занятость» живёт до истечения TTL.
Не выбрано: без lease нельзя совместить недолгую транзакцию с взаимоблокировкой.

**Внешний координатор (etcd, ZooKeeper).** Для: аренды с продлением — их
основной сценарий, есть готовые реализации, гарантии консистентности и
наблюдаемости лучше, чем при самописном решении поверх БД.
Против: целый сервис ради координации. В PostgreSQL уже есть всё
необходимое — уникальный индекс, транзакции, серверные часы, `SKIP LOCKED`.
Введение внешнего координатора добавляет точка отказа и операционную сложность
ради функциональности, которая укладывается в три колонки.
Не выбрано.
