# ADR-0013: Обработчики ограничены белым списком модулей

**Статус**: Accepted
**Дата**: 2026-10-11
**Область**: исполнение шагов, безопасность

## Контекст

Дефинишен ссылается на код строкой `module:function`, и движок импортирует
модуль в момент исполнения шага (`app/handlers/registry.py`). Валидация
проверяет, что обработчик существует и импортируется, но не проверяет, откуда
он взят.

Определение сохраняется через HTTP (`POST /api/definitions`) без
разграничения прав. Значит, кто умеет пользоваться редактором, может указать
`os:system` — и код выполнится в процессе воркера с его правами.

Для курсовой работы это свойство движка, а не уязвимость: расширяемость через
дефинишен и есть механизм. Но граница не была записана, и следующий читатель
кода принял бы её за ошибку, а не за решение.

## Решение

Ограничить импорт списком разрешённых корней модулей. По умолчанию
`app.`: обработчик может лежать в приложении, но не в стандартной библиотеке и
не в стороннем пакете. Список задаётся настройкой
`handler_module_allowlist`, поэтому добавление нового домена остаётся
конфигурацией, а не правкой кода.

Проверка живёт в `resolve_handler` — там, где происходит импорт. Валидация
дефинишена зовёт ту же функцию, поэтому отказ находится при сохранении, а не
через час после запуска инстанса.

## Последствия

### Положительные

- Определение из редактора не может вызвать произвольный код.
- Правило одно и то же в двух местах: реестр и валидация не могут разойтись.
- Расширение движка остаётся возможным: достаточно добавить свой корень в
  настройку.

### Отрицательные

- Новое расширение требует настройки, а не только модуля в проекте. Это ровно
  та цена, которую платит граница.
- Список корней — регулярное выражение, а не импорт: опечатка в настройке
  тихо сузит или расширит область. Поэтому значение по умолчанию узкое, а
  тест фиксирует его.
- Внешние обработчики, поставленные в site-packages, перестают работать без
  явного разрешения. Для проекта без плагинов это не потеря.

### Нейтральные

- Поведение определений, сохранённых ранее, не меняется: все они ссылаются на
  `app.demo.handlers`.

## Рассмотренные альтернативы

1. **Ничего не ограничивать, описать в документации.** Самое дешёвое, но
   свойство «дефинишен исполняет произвольный код» остаётся невидимым для
   читателя и не проверяется ничем.
2. **Разрешить только явно перечисленные обработчики.** Надёжнее по
   безопасности, но превращает определение в закрытый список и убивает главное
   свойство: добавить процесс без изменения кода движка.
3. **Отдельный процесс выполнения без прав.** Правильно по существу, но это
   отдельный сервис с протоколом и собственной отказоустойчивостью — заметно
   больше работы, чем задача позволяет в этом заходе.
