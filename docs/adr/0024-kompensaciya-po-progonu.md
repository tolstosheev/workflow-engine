# ADR-0024: Компенсация опознаётся по прогону шага, а не по имени

**Статус**: Accepted
**Дата**: 2026-10-17
**Область**: Saga, идемпотентность

## Контекст

ADR-0004 определяет компенсацию как отмену «уже свершившихся действий», а ADR-0010
задаёт ключ компенсации как `compensate:{step_name}`. Обе формулировки молча
считают, что у шага есть одно выполнение.

Цикл это предположение ломает. Шаг, объявленный с `loop`, выполняется несколько
раз, и каждое выполнение — отдельный бизнес-эффект: резерв берётся заново. Репетиция
на стенде показала это данными: процесс с циклом зарезервировал шесть единиц и
вернул три, а сам остался `COMPENSATED`. Три единицы остались на складе навсегда.

Причин было три, и каждая выглядела исправной по отдельности:

- план отката искал «последнее успешное выполнение шага» одним запросом с
  ограничением в одну строку, поэтому все проходы получали один `step_run_id`;
- ключ компенсации строился по имени шага, поэтому два прохода хотели один ключ;
- контекст обработчика содержал **тот же** ключ, собранный во втором месте, —
  формат был записан дважды.

Вторая и третья компенсации приходили под занятым ключом и возвращали «уже
применено» — успех без отмены. Обратный порядок это скрывает: повторно откатывать
шаг, который уже откатан, никто не смотрит.

## Решение

1. **Единица компенсации — выполнение шага, то есть прогон.** План берёт все
   неоткатанные прогоны шага, а не «последний»: цикл выполнен трижды — три
   компенсации.
2. **Ключ включает прогон:** `{instance}:compensate:{шаг}:{step_run_id}`. Номер
   попытки по-прежнему не входит: падение между эффектом и отметкой вернуло бы
   средства второй раз (ADR-0010).
3. **Формат ключа пишется один раз** — в `saga.operation_key`, и обработчик
   получает его в `ctx.operation_id` снаружи. Собранный в двух местах формат и
   разошёлся именно так.
4. **Порядок группируется по шагу.** Внутри шага он строго обратный, между шагами —
   по порядку шагов из журнала. Разбор хранит выполненные шаги без повторов, и
   строгий обратный порядок по проходам из него недоступен.

## Последствия

### Положительные

- Резерв перестаёт утекать: на живом стенде процесс с циклом после отката
  показывает «зарезервировано 6, возвращено 6».
- Ключ компенсации стал выводим из данных отката, а не из имени шага: тот же
  прогон всегда даёт тот же ключ, и это проверяемо.
- Ошибка «уже применено, но ничего не отменено» стала невозможной по построению:
  разные выполнения физически не могут получить один ключ.

### Отрицательные

- **Порядок компенсаций перестал быть строго обратным по проходам.** Для шага,
  выполнявшегося несколько раз, его компенсации идут подряд, а не чередуются с
  компенсациями соседних шагов. В предметной области это безопасно: деньги
  возвращаются раньше, чем товар уходит со склада. Для области, где порядок
  внутри цикла важен, решение не подходит — и это граница, а не мелочь.
- **Ключи в `processed_operations` стали длиннее** (около 110 символов вместо
  60) и перестают читаться глазом в таблице. Столбец это вмещает, а читать их
  вручную смысла не осталось.
- **Планы отката стали длиннее.** Процесс с десятью проходами цикла получает
  десять компенсаций одного шага, и на экране отката это выглядит повтором —
  поэтому полоса порядка показывает проходы явно, а не по именам шагов.

### Нейтральные

- Отметка `compensated` в `step_runs` теперь принадлежит прогону, а не шагу, и
  это совпадает со смыслом колонки; схема БД не менялась.
- Старые ключи вида `compensate:{шаг}` остаются в таблице для процессов,
  откатанных до этого решения. Повтор их отката невозможен: шаг помечен
  `compensated`, а план его не берёт.

## Рассмотренные альтернативы

**Хранить повторы в состоянии разбора и отдавать полную
последовательность выполнений.** Даёт строгий обратный порядок по проходам и
снимает группировку. Против — появляется второе представление о выполненных шагах
рядом с `completed_steps` без повторов, и это ровно тот класс дефекта, который
проект уже ловил: два ответа на вопрос «что выполнено», из которых один врёт.
Отклонено; граница записана в ADR и в `ENGINE.md`.

**Одна компенсация на шаг, отменяющая всё его выполнения разом.** Дёшево и
понятно на схеме без циклов. Против — обработчик не знает, сколько раз
выполнялся шаг и по сколько единиц брал каждый раз: на демо-складе это означало бы
отменять по заявленному количеству, а при разных итерациях количество разное.
Отклонено.

**Компенсировать только последнее выполнение, но честно объявить это.** Не
меняет кода, но оставляет резерв в силе — то есть компенсацию, которая не
компенсирует. Против ровно тот факт, который нашли на стенде. Отклонено.
