# ADR-0006: Формат определения workflow

| | |
|---|---|
| **Status** | Proposed |
| **Date** | 2026-10-08 |
| **Deciders** | команда проекта |

## Context

Процессы должны задаваться **данными**, а не кодом: иначе добавление нового
процесса означает изменение и выпуск движка.

Формат определения определяет, что может выразить язык: ветвления,
параллельные ветки, ожидания, компенсации. От него зависят и трассировка
дефинишенов, и валидация, и отображение в интерфейсе.

Требования к формату:

- описать граф шагов с переходами, ветвлениями и параллельными ветками;
- объявить компенсации явно, поимённо;
- задать таймауты, повторы и циклы с пределом;
- резолвить обработчик в код по строке, без генерации;
- валидироваться структурно (схема) и семантически (граф).

## Decision

Формат — **JSON** (`jsonb` в `workflow_definitions.definition`) со схемой на
Pydantic v2. Ядро описания:

```json
{
  "start": "validate_cart",
  "steps": {
    "validate_cart": {
      "action": "app.demo.handlers.inventory:validate_cart",
      "next": "reserve_inventory"
    },
    "reserve_inventory": {
      "action": "app.demo.handlers.inventory:reserve_inventory",
      "compensation": "app.demo.handlers.inventory:release_inventory",
      "next": "charge_payment"
    },
    "charge_payment": {
      "action": "app.demo.handlers.payment:charge",
      "compensation": "app.demo.handlers.payment:refund",
      "next": "create_shipment",
      "retry": { "max_attempts": 3, "backoff_seconds": 2 }
    },
    "confirm_delivery": {
      "action": "app.demo.handlers.shipment:confirm",
      "wait_before_seconds": 60
    }
  }
}
```

| Ключ | Смысл |
|---|---|
| `start` | Первый шаг; обязателен |
| `steps` | Именованный граф шагов |
| `action` | Обработчик как `module:function` |
| `compensation` | Обработчик компенсации |
| `next` | Следующий шаг; объект `{"on_success": ..., "on_failure": ...}` — ветвление |
| `retry` | `max_attempts`, `backoff_seconds` |
| `wait_before_seconds` | Durable-ожидание перед шагом |
| `loop` | Явный признак цикла с `max_iterations` |
| `fork` / `join` | Параллельные ветки |
| `timeout_seconds` | Таймаут шага |

Валидация двух уровней:

| Уровень | Что проверяет | Когда |
|---|---|---|
| Структурный | Типы, обязательные поля, форматы | Pydantic при разборе |
| Семантический | Разрешимость `next` и компенсаций, отсутствие бесконечных циклов, импортируемость обработчиков | `definition_service` |

## Consequences

**Positive:**

- Pydantic даёт одну схему для валидации дефинишена и для генерации контракта
  API. Расхождение схемы и поведения обнаруживается при разборе, а не при
  исполнении.
- Обработчик задаётся строкой `module:function` — новый домен подключается
  без изменения движка. Резолв через `importlib` работает с любым кодом,
  удовлетворяющим сигнатуре.
- Компенсация объявлена явно и поимённо: её отсутствие видно в дефинишене, а
  не выясняется при откате.
- JSONB позволяет менять формат без миграции БД и строить индексы по полям
  при необходимости.
- JSON однозначно печатается в интерфейсе и принимается в любом редакторе.

**Negative:**

- **Слабая типизация.** Ошибка в ключе (`compansation` вместо `compensation`)
  не мешает разбору JSON — её поймает только семантическая валидация. Для
  дефинишенов, написанных вручную, это источник неприятных сюрпризов.
- **Компенсация не обязательна.** Схема не может потребовать её для каждого
  шага: некоторые шаги (валидация, подтверждение) обратимы по умолчанию.
  Пропущенная компенсация у платёжного шага обнаружится только при откате.
  Вместо ошибки валидации введено предупреждение в ответе
  `POST /definitions/{id}/validate` — компромисс, осознанно выбранный в
  пользу простоты описания.
- JSON не комментируется. В сложном процессе пояснения приходится держать в
  поле описания, что слабее комментариев в коде.
- Резолв `module:function` в рантайме означает, что ошибка импорта проявится
  при исполнении, а не при развёртывании. Проверка импортируемости в
  семантической валидации частично снимает проблему, но не полностью: обработчик
  может импортироваться и всё равно падать при вызове.
- Выбор JSON перед YAML: YAML короче и позволяет комментарии, но требует
  дополнительной зависимости и допускает неоднозначный разбор (отступы,
  неявные типы). API уже обменивается JSON, поэтому второй формат создал бы
  ещё одно преобразование.

## Alternatives considered

**YAML.** Для: читается человеком без усилий, поддерживает комментарии —
критично для дефинишенов, которые пишут и правят вручную; отступы вместо
скобок убирают шум. Ключевой довод «за» — вполне серьёзный, и для
декларативных конфигураций YAML действительно удобнее.
Против: неоднозначность разбора (значение `on` против `True`, `no` против
`False`), ошибки отступов вместо ошибок JSON, и необходимость отдельной
зависимости для парсинга. JSON используется уже в API, поэтому YAML добавил бы
преобразование «YAML → JSON → объект». Не выбрано: для дефинишенов,
которые в основном генерируются скриптами и редактируются через валидируемую
форму в интерфейсе, JSON проще; при росте доли ручного редактирования
возврат к YAML — естественное развитие.

**Python-модуль с описанием процесса в коде.** Для: полная выразительность
(условия, циклы, вычисления), проверка типов mypy, рефакторинг работает
штатно, отладка в привычной среде.
Против: добавление процесса требует изменения кода и выпуска — ровно то, чего
ADR-0002 и сам проект требуют избежать. Процесс перестаёт быть данными,
трассировка и версионирование дефинишенов ломаются.
Не выбрано: возвращает к жёсткой связи «процесс = код».

**Protobuf / gRPC-описание графа.** Для: бинарный формат, компактность,
строгая схема на этапе компиляции, версионирование полей, зрелые инструменты.
Против: нечитаемо без тулчейна — валидация и правка в интерфейсе потребуют
специального редактора бинарных дефинишенов. Для курсовой работы удобство
показать определение в тексте сильно перевешивает строгость схемы.
Не выбрано.

**SQL-таблицы `definition_steps` и `definition_transitions` вместо JSONB.**
Для: реляционная целостность, внешние ключи, удобные запросы по шагам,
`JOIN` для переходов.
Против: структура графа известна только в момент запуска инстанса, а формат
дефинишена меняется приложением. Нормализованные таблицы дают жёсткую схему
под текущий формат: изменение формата требует миграции, а переходы и
компенсации — моделировать в реляционной схеме, где они плохо выражаются
(компенсация — не переход, а обратное действие).
Не выбрано: JSONB проще и гибче; если понадобится поиск по шагам, добавится
GIN-индекс.

**Формат с явным массивом шагов и переходов (`steps: [...]`,
`transitions: [...]` вместо именованного объекта).** Для: порядок шагов
сохраняется в разборе, появляется возможность сослаться на шаг по индексу,
одинаковая структура для любых идентификаторов.
Против: ссылки по индексу хрупки: вставка шага в середину сдвигает все
остальные. Именованный объект делает переходы читаемыми прямо в тексте —
`"next": "reserve_inventory"` понятнее, чем `"next": 2`. Не выбрано.

**Визуальный редактор с графом как основным носителем (формат — производный от
UI).** Для: рисуешь процесс — получаешь корректный дефинишен; редактор
исключает ошибки ссылок; основная форма изучается интуитивно.
Против: выбранный редактор диктует ограничения (например, отсутствие
условных переходов); граф в виде изображения не поддается diff и ревью; JSON
остаётся полезнее для скриптов и версионирования. В проекте редактор
предусмотрен как способ ввода, но носителем остаётся JSON.
Не выбрано: редактор реализуется поверх JSON, а не вместо него.
