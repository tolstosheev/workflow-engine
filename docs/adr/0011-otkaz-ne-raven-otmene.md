# ADR-0011: Отказ без компенсации отличается от отмены

| | | |
|---|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-10 |
| **Deciders** | автор проекта |
| **Связано с** | ADR-0004 (Saga с компенсациями), ADR-0006 (формат определения) |

## Context

Когда компенсировать нечего, `_compensate` завершал инстанс статусом
`CANCELLED`. Один и тот же терминальный статус получали два несовпадающих
исхода:

- пользователь запросил отмену, но откатывать было нечего — процесс отменён;
- шаг упал, компенсировать нечего, никто ничего не отменял — процесс тоже
  помечался как отменённый.

Второй случай вводит в журнал ложь. `INSTANCE_CANCELLED` в истории событий
после отказа шага означает, что отмену кто-то просил, а её не было.

Дополнительно расходились два места, решающих одно и то же. `finish` писал
`INSTANCE_COMPENSATED` для любого статуса, которого не было в словаре, — то
есть отказ без компенсации утверждал в журнале «откат завершён», хотя никакого
отката не было. Это не опечатка в подписи, а подмена терминального события:
`replay` получал `COMPENSATED`, и состояние инстанса становилось таким,
которым никогда не было.

Третье место. `retry_compensation` менял статус колонкой, без события. Для
пользователя это выглядело как «повтор отката запущен», но `replay` не видел
ничего нового и навсегда оставлял `COMPENSATION_FAILED`. Воркер, подхвативший
инстанс после перезапуска, видел отказ и не стал бы повторять компенсацию, даже
если повтор и был нужен.

Все три расхождения — следствие одного решения, принятого неявно: у пустого
отката не было собственного исхода, и для него подставлялось чужое событие.

## Decision

**У пустого отката два разных исхода, и журнал различает их явно.**

- Добавлено событие `INSTANCE_FAILED` — отказ шага, компенсировать было нечего. Отдельное событие, а не переиспользование `INSTANCE_COMPENSATED`:
  переиспользование продолжало бы утверждать несуществующий откат.
- `replay` переводит `INSTANCE_FAILED` в `InstanceStatus.FAILED` и обнуляет
  `current_step`.
- `InstanceState.cancel_requested` помнит, чем вызван откат. Флаг выставляется
  событием `INSTANCE_CANCEL_REQUESTED` и сбрасывается терминальным
  `STEP_FAILED`: события обрабатываются по порядку, поэтому побеждает
  последнее, то есть причина актуальна.
- `_compensate` при пустом плане выбирает терминальный статус по этому флагу:
  `CANCELLED` при отмене, `FAILED` при отказе.
- `retry_compensation` пишет `COMPENSATION_STARTED` с признаком `retried`.
  Статус меняется только через событие, как и любое другое изменение (§3.1).

## Consequences

**Positive:**

- Журнал перестаёт утверждать то, чего не было: отказ читается как отказ.
- `replay` и колонка инстанса сходятся после ручного повтора компенсации, а
  расходятся только в момент, когда запись ещё не зафиксирована.
- Перезапуск воркера после `retry_compensation` продолжает откат, а не
  застревает в `COMPENSATION_FAILED`.
- В интерфейсе появилось различимое состояние «Ошибка» и событие с подписью,
  а не безымянная отмена.
- Флаг `cancel_requested` читается прямо при отладке и объясняет, почему
  инстанс пришёл в тот или иной терминальный статус.

**Negative:**

- **Флаг в состоянии вместо типа терминального события.** Причину отката
  приходится хранить флагом, а не выводить из последнего события. При появлении
  третьего источника (таймаут инстанса, принудительная остановка) флаг
  придётся расширять, иначе новый случай молча попадёт в одну из двух
  существующих веток.
- **Решение принимается на записи события, а не на чтении.** Флаг меняет
  прошлое событие: `STEP_FAILED` в момент записи не знал, что отмену не
  просили. Отсюда два места, читающих флаг, должны быть согласованы с
  порядком событий — ошибка в порядке даст неверный статус при пустом откате.
- **Состояния `FAILED` и `COMPENSATED` требуют объяснения в интерфейсе.**
  Пользователь видит два «неуспешных» исхода и должен различать их по
  подписи; без подписи они неотличимы.
- **Новое событие — это изменение контракта.** Клиенты, перечисляющие типы
  событий, обязаны его учесть: поток SSE, словарь подписей, хранилище в
  zustand. Расхождение проявляется не сразу: неизвестное событие просто
  игнорируется, и строка инстанса какое-то время показывает устаревший статус.
- **`CANCELLED` при отмене без компенсаций остаётся спорным по смыслу.**
  Формально процесс не отменялся — его нечего было отменять. Сохранение
  поведения сделано ради совместимости с существующими тестами и ожиданиями
  интерфейса, но статус можно было бы заменить на `FAILED` и там тоже.

## Alternatives considered

- **Оставить `CANCELLED` для обоих случаев.** Довод за: ноль изменений, одно
  событие, никакой новой сущности. Довод против: журнал при отказе шага
  утверждает, что отмену запросили, а её не было; это ровно тот расхождение
  между событием и действительностью, ради устранения которого журнал и
  существует. Отвергнуто.
- **Переиспользовать `INSTANCE_COMPENSATED` с флагом в payload** вместо нового
  события. Довод за: событие не добавляется, подписчики не меняются. Довод
  против: событие перестаёт означать своё имя, а payload становится
  обязательным для понимания состояния. Отвергнуто — лучше явное событие, чем
  неявный флаг в данных события.
- **Выводить причину отката из последнего события при чтении**, не храня флаг.
  Довод за: никакого нового поля в состоянии, причина всегда актуальна.
  Довод против: требует просмотра истории при каждом вычислении статуса, то
  есть либо второго прохода по журналу, либо хранения истории — а состояние
  для того и пересчитывается, чтобы быть единственным источником для
  вывода. Отвергнуто.
- **Считать отказ без компенсаций отменой, но переименовать статус в
  «завершён без отката».** Довод за: один статус, честная подпись. Довод
  против: пришлось бы различать ещё и успешные завершения без компенсаций, то
  есть статус стал бы означать «терминально» и потерял бы конкретику. Отвергнуто.
