# ADR

Architecture Decision Records — принятые архитектурные решения и причины,
по которым они приняты.

Формат — Nygard: Context / Decision / Consequences (Positive / Negative /
Neutral) / Alternatives considered / References. Раздел **Negative** обязателен
и не может быть пустым: решение без видимой цены не бывает честным.

## Статусы

| Статус | Значение |
|---|---|
| `Proposed` | обсуждается, код ещё не написан |
| `Accepted` | принято и реализуется |
| `Superseded by ADR-XXX` | заменено более поздним решением |

Принятый ADR неизменяем. Новый контекст — новый ADR, в старом меняется только
строка `Status`.

Реализация: ADR-0001 — в Фазе 0, ADR-0002…0006 — в Фазе 1 (схема данных и
валидация дефинишена), ADR-0002…0005 в объёме ядра — в Фазе 2, ADR-0007 — в
Фазе 5 (замеры и методика их проведения), ADR-0008 — в Фазе 7, ADR-0009…0011 — в релизе 1.2.1 (исправления дефектов отката и повторов, обнаружение повторов и различие отказа с отменой), ADR-0012 — при разборе стенда: метрики воркера не достигали `/metrics`, ADR-0014 — при разборе стенда: единственный способ ждать неизвестный срок был выдумать его числом.

ADR-0022 — там же, где нашлась подмена: глобальное правило инъекции досталось
чужому процессу, и сценарий отработал успехом, доказав не то.

ADR-0019 и ADR-0020 — по решению владельца: уборка журнала служебным путём (триггер пропускает удаление только для терминального архивного процесса) и снятие резерва при подтверждении доставки.

ADR-0015 — в Фазе 10: провал компенсации нечем было показать, потому что ломался только прямой шаг. ADR-0016 — долг из ADR-0014. ADR-0017 и ADR-0018 — при разборе стенда в Фазе 13: список забивался завершёнными процессами, а воркер без аренды не оставлял следов. ADR-0021 — там же: строки реестра копились, и заголовок «12 в системе» при трёх работающих контейнерах был неправдой.

ADR-0019 и ADR-0020 — `Proposed`: оба касаются собственных утверждений работы, и принять их решено не молча. Кода по ним нет; что именно изменится при принятии, записано в самих записях.
