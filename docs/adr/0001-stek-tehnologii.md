# ADR-0001: Выбор стека технологий

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Deciders** | команда проекта |

## Context

Проект — распределённый движок выполнения workflow с поддержкой долгих
транзакций и компенсаций. Требуется:

- исполнять шаги, которые могут жить минуты и часы, при этом не держать
  транзакцию БД открытой дольше нескольких миллисекунд;
- обеспечить переживание падения воркера посреди шага и продолжение работы с
  последнего durable-чекпоинта;
- гарантировать взаимноисключающее исполнение инстанса при нескольких воркерах;
- дать графический интерфейс с живым обновлением состояния;
- быть проверяемым: порог покрытия тестами 90% branch.

Ключевые технические требования — неблокирующий ввод-вывод (каждый шаг ждёт
внешний сервис), конкурентный доступ к PostgreSQL из нескольких процессов,
строгая типизация контракта между бэкендом и фронтендом.

## Decision

Бэкенд — **Python 3.13 + FastAPI**, доступ к данным — **SQLAlchemy 2.0 async**,
схема версионируется **Alembic**, хранилище — **PostgreSQL 16**. Фронтенд —
**React 19 + TypeScript + Vite + Tailwind CSS**, состояние UI — **zustand**,
живые обновления — **SSE**. Инфраструктура — **Docker Compose** с отдельным
сервисом для каждой реплики воркера.

## Consequences

**Positive:**

- `async`/`await` в Python выражает исполнение шагов без потоковых блокировок:
  один воркер держит сотни «спящих» инстансов, и каждый просыпается по событию
  из журнала, а не по таймеру в памяти процесса.
- `SELECT ... FOR UPDATE SKIP LOCKED` — ровно то, что нужно для распределённой
  очереди задач на готовой БД: PostgreSQL становится и хранилищем, и очередью,
  и координатором, без отдельного брокера сообщений.
- Pydantic v2 даёт валидацию дефинишена workflow и контракт API в одном
  описании: фронтенд генерирует типы из OpenAPI, расхождение обнаруживается
  компиляцией, а не в рантайме.
- SQLAlchemy 2.0 требует явчных транзакций (`session.begin()`), что делает
  границы чекпоинтов видимыми в коде — инвариант §3.2 `AGENTS.md` соблюдается
  структурно, а не по договорённости.
- Alembic даёт воспроизводимую схему: версия БД и версия кода определяют одно
  и то же состояние, что критично для восстановления после сбоя.

**Negative:**

- GIL ограничивает параллелизм на CPU-содержащих шагах. Приемлемо, потому что
  шаги I/O-тяжёлые (вызовы сервисов, ожидания), но обработка больших объёмов
  данных потребует выноса в `asyncio.to_thread` или отдельного сервиса.
- У Python нет встроенной статической типизации уровня Rust или Java; ошибки в
  типах ловятся mypy и тестами, а не компилятором. Отсюда требование
  `disallow_untyped_defs = true` — оно дорогое, но без него типизация
  декоративна.
- `asyncpg` — реализация протокола на Cython, и она официально поддерживает
  только CPython. Сборка под альтернативными интерпретаторами потребует
  замены драйвера.
- Docker Compose, в отличие от Kubernetes, не даёт автоматического
  перераспределения реплик при падении узла. Масштабирование ограничено
  одной машиной — приемлемо для учебной работы, но это осознанный потолок.
- Tailwind CSS 4 вносит классы прямо в разметку: длинные списки классов
  усложняют чтение JSX по сравнению с семантическими именами из CSS-модулей.

**Neutral:**

- Pydantic используется и для валидации дефинишенов, и для схем API — разделения
  на два слоя нет.
- zustand выбран вместо Redux Toolkit: меньше boilerplate, но и нет
  встроенной middleware-инфраструктуры для сложных сценариев.
- Vitest в проекте не используется: тестирование фронтенда ограничено
  E2E-сценариями на Playwright, отдельного порога покрытия для TS-кода нет.

## Alternatives considered

**Java 21 + Spring Boot 3.** Для: Java — самый распространённый язык в
дисциплине «Интернет-программирование», у неё развитая экосистема для
распределённых систем (Spring StateMachine, Camunda как готовый движок
процессов), строгая статическая типизация ловит ошибки до запуска, а
`@Transactional` даёт осмысленные транзакционные границы «из коробки».
Против: в окружении разработки JDK отсутствует, сборка и запуск медленнее,
и объём кода для того же результата больше — компонентная модель Spring
требует больше настройки на каждый элемент. Не выбрано: потеря времени на
установку и настройку среды при готовом Python-окружении и отсутствии
опыта промышленной Java-разработки в проекте.

**Node.js + TypeScript (NestJS).** Для: один язык на фронтенде и бэкенде —
общие типы без генерации из OpenAPI, EventSource для SSE работает нативно,
команда фронтенда не переключает язык.
Против: управляемая транзакция БД — главный инструмент проекта — в Node
значительно слабее (нет полноценного аналога `session.begin()` с откатом на
уровне соединения), а однопоточная модель исполнения усложняет картину
«воркер спит, пока не пришло событие». Не выбрано: корректность транзакционных
границ здесь важнее единого языка.

**Temporal (Python SDK) вместо собственного движка.** Для: Temporal решает ровно
эту задачу — durable execution с компенсациями, таймерами и восстановлением
после падения воркера, и решает её лучше, чем самодельная реализация;
экономит месяцы разработки, в нём есть визуализация и зрелый набор тестов.
Против: тема курсовой — именно разработка такого движка; использование
Temporal свело бы работу к обёртке над готовым решением. Не выбрано сознательно:
внешний движок рассматривается как эталон и как объект сравнения в разделе
«Анализ аналогов», но в основе системы не используется.

**Node.js + PostgreSQL + отдельный брокер (Redis Streams, Kafka).** Для: Kafka
даёт готовые гарантии доставки и потребительские группы, Redis Streams — лёгкий
брокер, снимающий нагрузку с БД и дающий низкую задержку подбора задач.
Против: вторая точка отказа и второй источник состояния. Идемпотентность всё
равно пришлось бы реализовывать в прикладном коде, а корректность при
частичных сбоях — отслеживать в двух системах сразу. Не выбрано: одна БД с
`SKIP LOCKED` покрывает нагрузку курсовой работы и оставляет единственный
источник истины — журнал событий в той же транзакции, что и изменение состояния.
