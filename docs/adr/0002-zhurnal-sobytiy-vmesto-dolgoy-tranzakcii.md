# ADR-0002: Журнал событий вместо долгой транзакции БД

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-10-08 |
| **Deciders** | команда проекта |

## Context

Бизнес-транзакция проекта длится минуты и часы: резерв товара, ожидание оплаты,
передача в доставку, подтверждение получения. Транзакция PostgreSQL в это
время может удерживаться секунды.

Стандартный подход — открыть транзакцию на весь процесс и держать блокировки
до финиша. Для этой задачи он неприменим по трём причинам:

1. **Блокировки.** Строка резерва остаётся заблокированной на час. Любая
   другая операция с этим товаром ждёт или падает по таймауту.
2. **Соединения.** Долгая транзакция удерживает соединение из пула. Десять
   таких инстансов исчерпывают пул целиком, и API перестаёт обслуживать даже
   короткие запросы.
3. **Падение.** Откат уничтожает часы работы. Процесс, дошедший до четвёртого
   шага из пяти, после сбоя начинается заново.

## Decision

Транзакция уровня бизнес-процесса выражается последовательностью коротких
коммитов. Каждый коммит записывает событие в append-only журнал
`workflow_events` и в той же транзакции применяет изменение состояния.
Текущее состояние инстанса выводится replay'ом журнала.

Ограничения, которые это влечёт:

- транзакция не пересекает `await` на внешний сервис;
- `UPDATE` и `DELETE` на `workflow_events` запрещены;
- `seq` монотонен и выделяется под блокировкой строки инстанса;
- произвольный `UPDATE workflow_instances SET status` запрещён — статус
  меняется только записью события.

## Consequences

**Positive:**

- Блокировки живут миллисекунды. Соседние операции с тем же товаром проходят.
- Падение воркера стоит максимум одного шага: события уже записаны, replay
  даёт точку продолжения.
- Журнал бесплатно даёт полную историю для разбора и отладочный интерфейс:
  таймлайн в UI строится прямо по нему.
- Процесс может ждать сутки между шагами, не удерживая ни соединения, ни
  блокировки.

**Negative:**

- Состояние в памяти — производная величина: любой чтещий код обязан сначала
  сделать `replay`, иначе он прочитает устаревшее `variables`. Это источник
  целого класса ошибок, и запрет на прямой `UPDATE status` — не формальность,
  а основная защита.
- Строгая последовательность `seq` требует блокировки строки инстанса при
  каждой записи. При большом потоке событий это узкое место.
- Replay линеен по числу событий. Инстанс с тысячами событий читается медленно;
  в перспективе нужна периодическая компрессия журнала, что усложняет
  проектирование.
- Один источник истины в БД означает, что горизонтальное масштабирование БД
  исключено без перехода на секционирование по `instance_id`.
- Запись события и изменение состояния обязаны быть в одной транзакции.
  Нарушение этого правила даёт событие без изменения или изменение без
  события — оба варианта ломают восстановление, и обнаружится это не сразу.

## Alternatives considered

**Долгая транзакция на весь процесс.** Для: единственный способ получить
настоящий ACID, привычная модель, нет места для расхождений между намерением
и фактом — транзакция либо применена целиком, либо никак.
Против: блокировки на часы, соединение из пула на часы, полная потеря работы
при сбое, невозможность ждать между шагами без удержания ресурсов. Для задачи,
где процесс живёт минуты и часы, это прямое противоречие предметной области.
Не выбрано: недостатки перечислены выше как исходная постановка задачи.

**Optimistic concurrency на строке инстанса с версией.** Для: не удерживает
блокировки, проще в реализации, чем журнал, даёт защиту от гонок.
Против: не решает главное — при сбое на четвёртом шаге теряются все четыре.
Версия показывает конфликт, но не даёт продолжения с места остановки. Это
решает задачу конкурентного доступа, а не задачу долгой транзакции.
Не выбрано.

**Очередь сообщений (Kafka, RabbitMQ) вместо журнала в БД.** Для: журнал
изначально спроектирован как долговременный поток, гарантии доставки и
partition ordering из коробки, репликация и масштабирование не требуют
специальных мер.
Против: вторая система, которую надо разворачивать, мониторить и чинить.
Гарантия «событие и изменение состояния записаны вместе» в Kafka не
выражается: распределённая транзакция Kafka дорога, медленна и требует
отдельного координатора — то есть проблема возвращается на другом уровне.
Не выбрано: плата за вторую систему не даёт выигрыша, который даёт
PostgreSQL-транзакция.

**Snapshot + дельта (периодические снимки состояния плюс журнал).** Для:
replay ускоряется чтением ближайшего снимка вместо всей истории, журнал
можно усекать.
Против: снимок — это ещё одна точка истины, которая может разойтись с
журналом, и расхождение обнаружится как «инстанс в невозможном состоянии».
Для процесса из десятка шагов выигрыш в скорости replay не окупает
появление второго источника истины. Не выбрано.
