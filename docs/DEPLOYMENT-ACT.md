# Акт внедрения

Распределённый движок выполнения workflow с поддержкой долгих транзакций
и компенсаций.

| | |
|---|---|
| **Версия** | 0.6.0 |
| **Дата** | 2026-10-09 |
| **Основание** | выпускная квалификационная работа |
| **Статус** | введено в опытную эксплуатацию |

---

## 1. Назначение

Система исполняет бизнес-процессы, описанные данными, а не кодом: шаги с
переходами, ветвлениями, параллельными ветками, ожиданиями и компенсациями.

Ключевая задача — бизнес-транзакция, которая живёт минуты и часы. Классический
ACID для неё неприменим: удержание блокировки строк на час остановит всё
остальное, а падение процесса откатит часы работы. Решение — **durable
execution**: транзакция уровня бизнес-процесса выражается не блокировкой, а
последовательностью коротких коммитов в append-only журнале событий.

Демонстрационная предметная область — заказ: резерв товара → оплата →
отправление → подтверждение доставки, с компенсацией на каждом шаге.

## 2. Состав системы

### Ядро

| Подсистема | Модуль | Назначение |
|---|---|---|
| Журнал событий | `app/engine/journal.py` | Append-only журнал, источник истины, `replay` состояния |
| Интерпретатор | `app/engine/interpreter.py` | Переходы графа, ветвления, политика повторов |
| Lease | `app/engine/lease.py` | Взаимоисключающее исполнение инстанса между воркерами |
| Исполнитель шага | `app/engine/executor.py` | Транзакция до внешнего вызова и после |
| Saga | `app/engine/saga.py` | Компенсации в обратном порядке, попытки, `COMPENSATION_FAILED` |
| Таймеры | `app/engine/scheduler.py` | Durable-ожидания, переживающие рестарт |

## 3. Архитектурные решения

Все решения оформлены ADR и приняты осознанно, с зафиксированной ценой.

| ADR | Решение | Ключевая цена |
|---|---|---|
| 0001 | Стек: Python 3.13, FastAPI, PostgreSQL 16, React 19 | Ветка или версия без готовой поддержки требует форка |
| 0002 | Журнал событий вместо долгой транзакции | Один процесс пишет в поток — нужны блокировки на `seq` |
| 0003 | Lease вместо распределённых блокировок | Время обнаружения смерти воркера равно TTL |
| 0004 | Saga вместо 2PC | Компенсация не гарантирует атомарность — нужна идемпотентность |
| 0005 | At-least-once + идемпотентность | Каждая операция пишет в БД, это удлиняет критический путь |
| 0006 | Формат определения — JSON | Ошибка в ключе видна только семантической валидации |
| 0007 | Методика измерения производительности | Нагрузка генерируется тем же API, который замеряется |

## 4. Ключевые инварианты

Проверены тестами; каждый механизм имеет отдельный тест.

| Инвариант | Реализация | Чем проверяется |
|---|---|---|
| Журнал — единственный источник истины | Таблица append-only, триггер запрещает `UPDATE`/`DELETE` | `test_journal.py`, проверки на попытку правки |
| Состояние выводится replay'ом | Чистая функция от списка событий | `test_execution.py`, `test_worker_crash.py` |
| Транзакция не пересекает внешний вызов | Шаг открывает транзакцию до и после вызова | `test_execution.py` |
| Один воркер на инстанс | Lease с heartbeat, `FOR UPDATE SKIP LOCKED` | `test_lease.py`, chaos-тесты |
| Повтор шага безопасен | `processed_operations` + ключ операции наружу | `test_idempotency.py` |
| Откат идёт в обратном порядке | План строится по `step_runs`, а не по структуре графа | `test_saga_and_timers.py` |
| Провал компенсации виден | `COMPENSATION_FAILED` и ручной повтор | `test_saga_and_timers.py` |
| Ожидание переживает рестарт | Таймер в БД, срабатывание одной транзакцией | `test_durable_timers.py` |
| Шаг не выполнится дважды | Идемпотентный ключ проверяется до эффекта | `test_execution.py` |
| Ветвление по результату шага исполняется | `next` как объект, решение едет в журнале | `test_execution.py` |

### 5.2 Отказоустойчивость

Chaos-тесты поднимают воркер отдельным процессом и имитируют:

- убийство воркера посреди шага — инстанс подхватывается другим воркером;
- истечение аренды — перехват другим воркером;
- таймаут шага — инстанс остаётся восстановимым;
- конкуренция двух воркеров — они обрабатывают разные инстансы;
- проверка, что после перехвата нет дублей шагов и повторных эффектов.

### 5.3 Производительность

Условия: Intel Core i5-12450H (8 ядер / 12 потоков), 15.7 ГБ, PostgreSQL 16.15,
Docker 27.4.0, машина без посторонней нагрузки, 300 инстансов на прогон.

| Воркеров | Throughput | Время прохода |
|---|---|---|
| 1 | 2.8 инстанса/с | 105.3 с |
| 2 | 5.4 инстанса/с | 55.1 с |
| 4 | 10.3 инстанса/с | 29.1 с |

Масштабирование линейное (×1.9 на каждое удвоение). Длительность шага —
19–22 мс, медиана и среднее расходятся на 3–5%, то есть тяжёлого хвоста нет.
Время компенсации — 32 мс при одном воркере и 41 мс при четырёх, что
сопоставимо с двумя шагами.

Полные таблицы и методика — в [`BENCHMARKS.md`](BENCHMARKS.md) и
[ADR-0007](adr/0007-metodika-zmerov.md).

### 5.4 Контрольный пример

Сбой на шаге оплаты приводит к автоматическому откату выполненных шагов в
обратном порядке. Проверено на живом стенде: 30 из 30 инстансов дошли до
`COMPENSATED`, ни одна компенсация не провалилась, в журнале присутствуют
`COMPENSATION_STARTED`, `COMPENSATION_COMPLETED`, `INSTANCE_COMPENSATED`.

## 6. Условия эксплуатации

### Развёртывание

```bash
cp .env.example .env
docker compose up -d --build
cd engine && python -m scripts.seed
```

Поднимаются: PostgreSQL (5434), API (8000), две реплики воркера, фронтенд (5173).
Миграции применяет служебный сервис `migrate` до старта остальных.

### Ресурсы

| Параметр | Значение | Обоснование |
|---|---|---|
| `LEASE_TTL_SECONDS` | 30 | Время обнаружения смерти воркера |
| `HEARTBEAT_INTERVAL_SECONDS` | 5 | Должно быть заметно меньше TTL |
| `WORKER_POLL_INTERVAL_SECONDS` | 1 | Пауза при пустой очереди |
| `STEP_MAX_ATTEMPTS` | 3 | Число попыток до отката |
| Пул БД на воркер | 10 + 20 | Первый ресурс, кончающийся при росте числа воркеров |

### Порядок обслуживания

| Задача | Команда |
|---|---|
| Проверка без БД | `make test-fast` |
| Полная проверка | `make check && make test` |
| Отказоустойчивость | `make test-chaos` |
| Сквозная проверка живой системы | `make smoke` |
| Замеры | `make bench` |

Тесты требуют свободной базы: они очищают таблицы через `TRUNCATE`, а
работающий воркер удерживает блокировки — вместе это даёт взаимоблокировку.
Перед тестами воркеров останавливают.

## 7. Границы применимости

Честное перечисление того, что система не делает.

1. **Предметная область не делает внешних вызовов.** Обработчики работают с
   данными в БД. Проверена транзакционная машина, а не интеграция с реальными
   сервисами.
2. **Параллельные ветки `fork` / `join` объявлены и валидируются, но не
   исполняются.** Схема их принимает, валидатор проверяет разрешимость, а
   исполнение после fork-шага завершает процесс: ветки не запускаются.
   Сериальное ветвление по результату шага (`next.on_success` и
   `next.on_failure`) работает.
3. **Масштабирование проверено до четырёх воркеров.** Дальше упругость
   ограничена пулом соединений и CPU PostgreSQL.
4. **Гарантия exactly-once не существует** — доставка at-least-once, а
   идемпотентность имитирует ровно один раз. Повтор шага безопасен только при
   идемпотентном обработчике; это обязанность прикладного кода, а не движка.
5. **Плата за ошибку — время.** Политика повторов растягивает период, в
   течение которого процесс висит на промежуточном состоянии.
6. **Интерфейс не авторизует пользователей.** Он предназначен для стенда и
   демонстрации.
7. **Метрики Prometheus собираются из БД при каждом запросе.** Это сознательный
   компромисс в пользу наблюдаемости после перезапуска воркера, а не в пользу
   скорости сбора.

## 8. Известные ограничения и направления развития

| Ограничение | Направление |
|---|---|
| Ветки `fork` / `join` не исполняются | Доработка интерпретатора и журнала для параллельных шагов |
| Нет авторизации и разграничения доступа | Аутентификация на API, роли на операции над инстансами |
| Замеры генерируются тем же API, что замеряется | Внешний генератор нагрузки (k6) для чистых измерений |
| Нет распределённой трассировки | Трассировка по `instance_id` через OpenTelemetry |
| Компенсация не проверяет себя на повтор у внешнего сервиса | Ключ операции передаётся наружу, но это обязанность сервиса |

подтверждены: долгие транзакции выражаются последовательностью коротких
коммитов, отказоустойчивость обеспечена lease и журналом событий, компенсации
выполняются в обратном порядке и не скрывают свои сбои.

Требования проверок выполнены: покрытие branch 92.86% при пороге 90%, все 383
теста проходят, замеры воспроизводимы и снабжены полным раскрытием условий.

направление развития.
