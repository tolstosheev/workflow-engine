# Эксплуатация

Разбор эксплуатации системы: запуск, наблюдаемость, типовые сбои и порядок
действий при них.

---

## 1. Развёртывание

```bash
cp .env.example .env
docker compose up -d --build
```

| Сервис | Порт | Назначение |
|---|---|---|
| `db` | 5434 | PostgreSQL 16 |
| `migrate` | — | Одноразовый: `alembic upgrade head` |
| `api` | 8000 | REST, SSE, метрики |
| `worker` | — | Воркер |
| `worker-2` | — | Воркер |
| `frontend` | 5173 | Интерфейс |

Порядок запуска задан зависимостями compose: `db` (здоров) → `migrate`
(завершился) → `api`, `worker`, `worker-2`. Воркер без миграций упал бы на
первом же запросе к несуществующей таблице.

### Параметры конфигурации

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LEASE_TTL_SECONDS` | 30 | Сколько воркер может молчать, прежде чем lease протухнет |
| `HEARTBEAT_INTERVAL_SECONDS` | 5 | Как часто продлевается lease; обязан быть меньше TTL |
| `WORKER_POLL_INTERVAL_SECONDS` | 1 | Пауза между циклами опроса |
| `WORKER_MAX_STEPS_PER_CYCLE` | 100 | Сколько шагов за цикл до перевыбора задачи |
| `STEP_MAX_ATTEMPTS` | 3 | Попыток на шаг до перехода к компенсации |
| `SSE_HEARTBEAT_SECONDS` | 15 | Heartbeat SSE, чтобы прокси не рвали соединение |

**Подбор `LEASE_TTL_SECONDS`** — главный эксплуатационный параметр:

| Значение | Последствие |
|---|---|
| Меньше времени самого долгого шага | Живой воркер признаётся мёртвым, шаг выполняется дважды |
| Значительно больше | Падение воркера обнаруживается слишком долго, инстанс «висит» |
| Равно `HEARTBEAT_INTERVAL_SECONDS` | Запрещено валидатором конфигурации |

Компромисс: TTL должен перекрывать максимальный таймаут шага плюс запас на
сетевые задержки. Для демонстрационного набора — 30 секунд при таймаутах шага
5–10 секунд.

### Масштабирование

Добавление реплик: копия сервиса `worker` в `docker-compose.yml`. Состояние в
БД, координация через lease — новая реплика сразу включается в работу.

Сколько воркеров в системе и кто из них молчит:

```bash
curl http://localhost:8000/api/workers
```

Воркер без аренды в списке процессов не виден: у него нет работы, а след в
системе остаётся только в реестре (ADR-0018). `state` отвечает `active`,
`stale` (молчит дольше `fresh_for_seconds`) или `stopped` (остановлен штатно).
Записи старше суток по умолчанию не выдаются — они скрыты за переключателем
«показать завершённых» вместе со своим числом, и в базе лежат на месте
(ADR-0021). Только что остановленный виден всегда: он объясняет, почему
процессы перестали продвигаться.

Упавший воркер из реестра не исчезает: «воркер молчит» и «воркера нет» —
разные вещи, и путать их нельзя.

### Уборка списка

`POST /api/instances/archive` убирает завершённые процессы **из списка**, а не
удаляет их: журнал остаётся целым, состояние по-прежнему выводится его
повтором, а процесс открывается по прямой ссылке (ADR-0017). Возврат —
`POST /api/instances/{id}/unarchive`.

Не архивируются `PAUSED` и `COMPENSATION_FAILED`: первый ждёт решения человека,
второй — повтора отката. Прятать их означало бы спрятать незакрытое.

Масштабирование БД не предусмотрено: журнал событий предполагает один источник
истины.

## 2. Наблюдаемость

### Журнал событий

Полный журнал — основной источник для разбора. Именно из него состояние
инстанса восстанавливается, поэтому расхождения в нём означают расхождения
в системе.

```bash
curl http://localhost:8000/api/instances/{id}/events
```

### Метрики

```bash
curl http://localhost:8000/metrics
```

| Метрика | Тип | Что показывает |
|---|---|---|
| `workflow_instances_total{status}` | gauge | Инстансы по состояниям |
| `workflow_steps_total{step,result}` | counter | Выполнения шагов: `success`/`failure` |
| `workflow_step_duration_seconds{step}` | histogram | Длительность шагов |
| `workflow_compensations_total{step,result}` | counter | Попытки компенсаций |
| `workflow_events_total{type}` | counter | События по типам |
| `worker_lease_acquired_total` | counter | Успешные захваты lease |
| `worker_lease_lost_total` | counter | Потерянные lease |
| `worker_recovered_instances_total` | counter | Инстансы, подхваченные после протухания |

**Что считать нормой:**

| Показатель | Ожидаемо |
|---|---|
| `workflow_instances_total{status="RUNNING"}` | Не растёт без новых запусков |
| `worker_lease_lost_total` | Близко к нулю; всплеск — воркер перегружен или TTL мал |
| `workflow_compensations_total{result="failure"}` | Ноль в норме; каждый случай — инцидент |
| `workflow_instances_total{status="COMPENSATION_FAILED"}` | Ноль в норме |
| `workflow_instances_total{status="PAUSED"}` | Растёт и не падает — процессы ждут человека. Если срок задан в определении, пауза обязана закончиться сама: рост без снятия означает, что срок не применён |

### Логи

```bash
docker compose logs -f worker
```

Включить JSON для агрегатора: `LOG_JSON=true`.

Каждая запись воркера содержит `worker_id` и `instance_id` — по ним
восстанавливается, кто обрабатывал инстанс и когда.

### Проверка состояния

```bash
curl http://localhost:8000/health
```

Проверка `SELECT 1` при старте: процесс без БД падает сразу, а не приходит к
пользователю с ошибкой на первом же запросе.

## 3. Типовые сбои

### 3.1 Инстанс завис в статусе `RUNNING`

**Признаки:** `updated_at` давно не менялся, lease протух, воркер его не
подхватывает.

**Причины:**

| Причина | Проверка |
|---|---|
| Воркер остановлен | `docker compose ps worker` |
| Попытки исчерпаны, компенсация не запустилась | Журнал: нет ни `STEP_FAILED`, ни `COMPENSATION_STARTED` |
| Шаг завис во внешнем вызове без таймаута | Логи воркера: нет `STEP_COMPLETED` после `STEP_STARTED` |

**Действия:**

```bash
# Кто владеет lease и когда он истекает
curl http://localhost:8000/api/instances/{id}

# Что происходило
curl http://localhost:8000/api/instances/{id}/events
```

Если lease истёк, а воркер жив, — перезапустите воркер. Если компенсация
должна была начаться, но не началась, — это дефект интерпретатора, а не
операционная ситуация.

### 3.2 Шаг выполнился дважды

**Признаки:** `workflow_steps_total{step}` больше числа `STEP_COMPLETED` в
журнале; в `processed_operations` две записи одного `op_key` (невозможно при
работающем ограничении) либо повторный внешний вызов.

**Причины:**

| Причина | Как проверить |
|---|---|
| TTL меньше длительности шага — lease протух на живом воркере | Сравнить `LEASE_TTL_SECONDS` с максимальной длительностью шага |
| Обработчик не проверяет `processed_operations` | Прочитать обработчик шага |
| Внешний сервис не идемпотентен по переданному ключу | Проверить, передаётся ли `op_key` наружу |

**Предупреждение:** повторный вызов без идемпотентного ключа — это дубль в
чужой системе, и откатить его штатно нельзя.

### 3.3 Компенсация не проходит

**Признаки:** статус `COMPENSATION_FAILED`.

Это не тихий сбой: часть выполненных шагов осталась в силе, инстанс не
приведён в исходное состояние.

```bash
curl http://localhost:8000/api/instances/{id}/steps   # что не компенсировано
```

**Порядок действий:**

1. Выяснить причину по `compensation_log.error`.
2. Устранить причину во внешней системе.
3. Запустить повтор:

```bash
curl -X POST http://localhost:8000/api/instances/{id}/compensation/retry
```

Компенсация необратима и идемпотентна: повтор безопасен. Компенсировать
компенсацию нельзя.

### 3.4 Очередь не разбирается

**Признаки:** число инстансов в `PENDING` растёт, `workflow_steps_total` не
увеличивается.

**Причины:**

| Причина | Проверка |
|---|---|
| Воркеров нет | `docker compose ps worker` |
| Воркер падает при старте | `docker compose logs worker` |
| Нет активного дефинишена | Проверить `is_active` у дефинишена |

### 3.5 Рост таблицы событий

Журнал append-only, поэтому растёт монотонно. Рост сам по себе дефектом не
является — это цена восстанавливаемости.

Сокращение возможно только вместе с политикой хранения:

| Стратегия | Условие |
|---|---|
| Полное хранение | Инстанс в работе или завершён недавно |
| Архив завершённых | Инстанс в терминальном состоянии дольше срока |
| Удаление | **Только** вместе с удалением самого инстанса |

Удаление событий незавершённых инстансов недопустимо: восстановление станет
невозможным.

### 3.6 SSE отваливается

**Признаки:** интерфейс перестал обновляться.

SSE требует отключённой буферизации и запрета сжатия на прокси. Heartbeat
раз в `SSE_HEARTBEAT_SECONDS` удерживает соединение, но прокси с коротким
таймаутом всё равно закроет его. Восстановление — стандартный `EventSource`
переподключается сам; на сервере гарантируется продолжение с последнего
полученного `seq`.

## 4. Регламентные проверки

| Периодичность | Что проверять |
|---|---|
| Непрерывно | `COMPENSATION_FAILED` — каждый случай разбирается вручную |
| Непрерывно | Рост числа инстансов в `RUNNING` без роста `workflow_steps_total` |
| Ежедневно | `worker_lease_lost_total` — ненулевое значение означает перегрузку или малый TTL |
| Еженедельно | Размер `workflow_events` и дисковое пространство |
| Перед защитой | Прогон `make check`, `make test`, контрольный сценарий |

### Метрики

`/metrics` отдаёт единый текст в экспозиционном формате Prometheus
(`text/plain; version=1.0.0`), а не OpenMetrics: строгий скрайпер отвергает
весь ответ из-за несоответствие заголовка.

Счётчики пишет воркер в своём процессе, поэтому для этого
каталога умерки общий, а `/metrics` собирает их из файлов (ADR-0012).

| Метрика | Источник | Что об ней |
|---|---|---|
| `workflow_instances_created_total` | API | создано инстансов |
| `workflow_lease_acquired_total` | воркер | успешные захваты аренды |
| `workflow_lease_lost_total` | воркер | аренда ушла другому воркеру |
| `workflow_step_duration_seconds` | воркер | распределение длительностей шагов |
| `workflow_instances` | база | инстансы по состояниям |
| `workflow_steps`, `workflow_compensations` | база | шаги и компенсации по результату |

### Каталог метрик

Каталог общий для всех процессов. Файлы называются по pid
процесса, поэтому у воркеров в Docker Compose включён `pid: host`: без него оба
воркера имели бы pid 1, писали бы в один файл, и счётчики терялись
бы без следа.

Каталог растёт по времени: воркер удаляет свои файлы при
остановке (`mark_process_dead`). Если каталог накто не удаляётся, файлы
падающего воркера остались бы навсегда: счётчик по прежнему
несвой инстанса учтён дважы.

Смена режима агрегата каталога (`mostrecent`) лучше убрать старые файлы:
замена режима обязательна любой строки стараых конфигурации.

### Проверка на стенде

`curl -s localhost:8000/metrics | grep workflow_lease` — счётчики воркера должны
быть выборками, и выводе она быльше ноля. Если метрика нет
в выводе вовсе — точно сделать по ней причине такие замеры
(`make load`).

### Повторы отката

Провал компенсации обязан перед повтором, и между попытками
по величине идёт пауза: пауза растёт по числу неудачных попыток и достигает
потолка.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `COMPENSATION_RETRY_BASE_SECONDS` | 5 | пауза перед первой попыткой |

### Срок ожидания человека

Срок задаётся в определении, полем `pause_timeout_seconds` рядом с
`wait_for: manual`, и не является настройкой движка: ожидание согласования и
ожидание публикации в чужом сервисе живут по разным правилам.

| Что видно | Что это значит |
|---|---|
| `PAUSED` держится дольше срока | Срок не применён: определение отправлено без него, либо процесс создан до этой правки |
| `INSTANCE_CANCEL_REQUESTED` с `reason: pause_deadline_expired` | Срок истёк штатно — процесс отменён и откатывается |
| Процесс в `PAUSED`, у которого в `timers` нет строки вида `pause_deadline` | Пауза без будильника: срок не задан, и процесс ждёт, пока придёт команда возобновления |

Истечение отменяет процесс, а не продолжает его: действие шага необратимо,
и «оплатить без согласования» — не то, что означают ворота согласования.
Без срока поведение прежнее — ждать, пока придёт человек.
| `COMPENSATION_RETRY_MAX_SECONDS` | 300 | потолок задержки |

Повторы не имеют предела: инстанс остаётся в `COMPENSATION_FAILED`,
пока служба не вернётся, и воркер берёт его сам (§3.5). Для
разбора сразу откат компенсации повторяется всё ещё.

## Пул соединений

Пул расчитывается на каждый **процесс**, а не на соединение: compose поднимает API и
два воркера. Каждый процесс держит до `DB_POOL_SIZE + DB_MAX_OVERFLOW` соединений,
и PostgreSQL считает их все независимо от того, заняты они сейчас или нет.

| Параметр | Значение |
|---|---|
| Максимум соединений на процесс | 10 (`DB_POOL_SIZE=5` + `DB_MAX_OVERFLOW=5`) |
| Предел числа процессов при `max_connections=100` | ≈ 9 (API + 8 воркеров) |

При 10 воркерах занято 90 из 100 слотов, а следующий процесс получает
`sorry, too many clients`. Если воркеров нужно больше, разводите API и воркеры по
отдельным экземплярам БД: у API больше одновременных занятых соединений, чем у
воркера, который обрабатывает инстансы строго по одному.

`DB_POOL_TIMEOUT` задан 5 с — это меньше TTL аренды в 30 с. Если соединений не
хватает, воркер ждёт 5 секунд, а не 30: иначе он потерял бы аренду именно в тот
момент, когда она истекла, и инстанс начал бы перехватываться каскадом.

`DB_POOL_RECYCLE` (1800 с) освобождает соединения любого возраста: прокси и
PgBouncer закрывают их между `pre_ping` и использованием.

```bash
# Сколько соединений занимает стенд:
docker compose exec db psql -U workflow -d workflow_engine -c \
  "SELECT count(*), state FROM pg_stat_activity WHERE datname='workflow_engine' GROUP BY state;"
```
## 5. Резервное копирование

Журнал событий — источник истины, его потеря означает потерю возможности
восстановления.

| Что | Как | Периодичность |
|---|---|---|
| `workflow_events` | `pg_dump` | Ежедневно |
| `workflow_instances`, `step_runs`, `timers` | `pg_dump` | Ежедневно |
| Таблицы предметной области | `pg_dump` | Ежедневно |

Восстановление в другой инстанс **не переносится**: в нём другие идентификаторы
дефинишенов. Переносится определение — через `POST /api/definitions`.

## 6. Контрольный сценарий

Проверка эксплуатационной готовности целиком.

```bash
# 1. Запуск окружения
docker compose up -d --build

# 2. Проверка состояния
curl http://localhost:8000/health

# 3. Создание дефинишена и запуск инстанса
curl -X POST http://localhost:8000/api/definitions -H "Content-Type: application/json" -d @definition.json
curl -X POST http://localhost:8000/api/instances -H "Content-Type: application/json" -d @instance.json

# 4. Наблюдение за исполнением
curl -N http://localhost:8000/api/stream

# 5. Проверка успешного завершения
curl http://localhost:8000/api/instances/{id}      # статус COMPLETED
curl http://localhost:8000/api/instances/{id}/events

# 6. Сбой на шаге оплаты с автоматическим откатом
curl -X POST http://localhost:8000/api/chaos/fail-step \
  -H "Content-Type: application/json" \
  -d '{"instance_id":"{id}","step":"charge_payment","mode":"always"}'
curl http://localhost:8000/api/instances/{id}      # статус COMPENSATED
curl http://localhost:8000/api/instances/{id}/steps # резерв возвращён

# 7. Восстановление после падения воркера
curl -X POST http://localhost:8000/api/chaos/stop-lease \
  -H "Content-Type: application/json" \
  -d '{"instance_id":"{id}","duration_seconds":40}'
sleep 35
curl http://localhost:8000/api/instances/{id}      # lease_owner сменился

# 8. Снятие инъекций
curl -X DELETE http://localhost:8000/api/chaos
```

Ожидаемый результат шага 6: инстанс в статусе `COMPENSATED`, резерв товара
снят, деньги не списаны. Ожидаемый результат шага 7: `lease_owner` отличается
от исходного, дублирующих шагов в журнале нет.

## 7. Сценарии показа

Страница «Сценарии» (`/scenarios`) собирает демонстрацию из уже существующих
ручек: правило инъекции, запуск процесса, действие по ходу, ожидание конца и
проверка утверждения по данным. Новых эндпоинтов бэкенда для этого нет.

Каждый сценарий объявляет ожидаемое состояние **и** свидетельства из журнала.
Состояния недостаточно: `COMPENSATED` бывает и у процесса, у которого резерв
остался на складе, поэтому подтверждением служит `COMPENSATION_COMPLETED`
с нужным `for_step`.

| Сценарий | Что показывает | Определение |
|---|---|---|
| Заказ проходит целиком | весь граф без компенсаций | `order_fulfillment` |
| Платёж отказывает, заказ откатывается | Saga в обратном порядке | `order_fulfillment` |
| Откат не проходит | `COMPENSATION_FAILED` виден и разбирается | `order_fulfillment` |
| Повтор отката | снятие причины и ручной повтор, возврат один раз | `order_fulfillment` |
| Повтор шага спасает процесс | at-least-once без отказа | `order_fulfillment` |
| Товара не хватает | постоянная ошибка без повторов | `order_fulfillment` |
| Отмена процесса | откат выполненных шагов при отмене | `order_with_wait` |
| Долгое ожидание | durable-таймер вместо sleep | `order_with_wait` |
| Ворота согласования | пауза человека и возобновление (ADR-0014) | `order_with_approval` |
| Срок ожидания истёк | отмена и откат по сроку (ADR-0016) | `order_with_pause_deadline` |
| Цикл исчерпан | `LOOP_EXHAUSTED` и откат | `order_with_loop` |
| Истечение аренды | перехват инстанса другим воркером | `order_with_wait` |
